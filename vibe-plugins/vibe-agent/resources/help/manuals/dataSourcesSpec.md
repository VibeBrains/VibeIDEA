# Подключения к БД: `.vibe/dataSources.json`

Самодостаточный документ: скопируйте его целиком своей модели и попросите собрать файл подключений —
в интернет за форматом ходить не придётся.

## Файл

```jsonc
{
  "dataSources": [
    {
      "id": "app",                                  // обязателен, уникален в файле
      "name": "Прод (только чтение)",               // необязательно; без него зовётся по id
      "url": "jdbc:postgresql://db.example.com:5432/app",   // обязателен
      "user": "reader",                             // необязательно
      "driverPath": "~/drivers/postgresql-42.7.11.jar",     // jar драйвера JDBC
      "driverClass": "org.postgresql.Driver",       // нужен только старым драйверам без сервиса
      "readOnly": true                              // правка данных не предлагается вовсе
    },
    { "id": "local", "url": "jdbc:sqlite:./dev.db" }
  ]
}
```

Массив можно писать и без обёртки: `[ { … }, { … } ]`.

**Пароля в файле нет и быть не может.** Файл живёт в git, а пароль в git — это утечка с
отложенным сроком. Пароль хранится в связке ключей системы (PasswordSafe платформы). Если поле
`password` в файле всё-таки окажется, панель скажет об этом красным: это не «неподдерживаемое
поле», а находка — секрет уже в репозитории.

Битая запись пропускается с указанием места, остальные подключения остаются рабочими: файл правят
руками, и опечатка в одном подключении не должна отключать все.

## Общий набор: поля `active` и `products`

Файлы `.vibe` приезжают из **общего набора**, который пишут несколько продуктов сразу — VibeIDE, VibeIDEA, дальше VibeCLI. Поэтому у записи есть два необязательных поля, отвечающих на **разные** вопросы: `active` — «включено ли», `products` — «кому адресовано». Запись бывает вашей и выключенной, и чужой и включённой у соседа.

| Поле | Значение |
|---|---|
| `active` | Включена ли запись. Поля нет — включена. `false` — запись описана и лежит на виду, но не работает. Именно так едут готовые образцы в засеянных файлах: сид — рабочий файл, а не двойник рядом с рабочим |
| `products` | Кому запись адресована: массив стабильных id в нижнем регистре — `vibeide`, `vibeidea`, `vibecli`. Поля нет — запись **для всех**, и это верно почти всегда |

На что можно рассчитывать:

- **Выключенная запись не проверяется вообще.** Она не выполнится, поэтому VibeIDEA молчит о её содержимом — не жалуется ни на незнакомое значение, ни на отсутствующую обязательную строку. Исключение одно: находки безопасности (пароль в `dataSources.json`) называются вслух и у выключенной записи — пароль уже лежит в репозитории, и выключенность записи его оттуда не убирает.
- **Запись не для этого продукта пропускается молча.** Это не ошибка и не предупреждение.
- **Незнакомый id продукта — тоже молча мимо.** Сборка, выпущенная сегодня, увидит запись для продукта, которого ещё нет, и промолчит.
- **`products` не защищает от старых сборок.** Сборка, которая о поле ещё не знает, игнорирует его и запись выполняет. Поэтому запись, которая пока не должна работать везде, едет выключенной — адрес и выключатель работают вместе, а не вместо друг друга.

```jsonc
// Запись, адресованная одному продукту и пока выключенная.
{ "products": ["vibeidea"], "active": false /* … остальные поля записи … */ }
```

## Драйверы

**Мы их не поставляем.** У драйверов разные лицензии (MySQL Connector/J — GPL с исключением для
свободного ПО), и класть их в дистрибутив значит принимать чужие условия за пользователя. Драйвер
скачивается один раз и указывается в `driverPath`:

| База | Драйвер | Лицензия |
|---|---|---|
| PostgreSQL | `org.postgresql:postgresql` | BSD-2 |
| SQLite | `org.xerial:sqlite-jdbc` | Apache-2.0 |
| MySQL | `com.mysql:mysql-connector-j` | GPL-2.0 + FOSS exception |
| MariaDB | `org.mariadb.jdbc:mariadb-java-client` | LGPL-2.1 |
| H2 | `com.h2database:h2` | MPL-2.0 / EPL-1.0 |

Каждый jar грузится **в своём загрузчике классов**: два драйвера разных версий в одном classpath
однажды встретятся, и разбираться в этом будет невозможно.

## Панель «БД»

Слева дерево объектов с поиском, справа консоль запросов и таблица результата — раскладка знакомая
по PhpStorm и DataGrip, потому что менять её незачем.

- **Двойной щелчок по таблице** — `SELECT * FROM … LIMIT 200` (число строк настраивается).
- **Пароль** — кнопка «Пароль…» в панели: он уходит в связку ключей системы. Пустой ввод удаляет
  сохранённый — «оставить как было» и «убрать» это разные желания.
- **Столбцы** видны в дереве по раскрытию таблицы.
- **Изменяющий оператор спрашивает подтверждение** и показывает, что именно уйдёт в базу:
  «выполнить» под курсором легко нажать случайно, а `DELETE` без `WHERE` отменить нечем.
- **Выгрузка CSV** — кнопкой; выгружается показанное, а не повторный запрос.
- Настройки (число строк, таймаут, показ системных схем) — Settings → Tools → VibeIDEA → «Базы данных».
- **«Выполнить»** — выполняется оператор, **внутри которого стоит курсор**; файл с десятком
  операторов не запускается целиком по случайному нажатию.
- Служебные схемы (`pg_catalog`, `information_schema`, `mysql`, `sys`, …) по умолчанию спрятаны:
  их десятки, и среди них теряются две схемы проекта.
- `NULL` печатается словом, а не пустотой: в базе это разные вещи, и человек, чинящий данные,
  обязан видеть, какая перед ним. Двоичное показывается размером, а не байтами.
- Одинаковые имена столбцов разводятся (`id`, `id (2)`): иначе `SELECT a.id, b.id` молча показывал
  бы один столбец вместо двух.

## Правка данных

Ячейка редактируема, только если правка **доказуемо адресуема**: результат открыт двойным щелчком
по таблице (то есть таблица известна) и её первичный ключ есть в самой выборке. Для запроса,
набранного руками, таблицу пришлось бы угадывать по тексту — а угаданный `UPDATE` выполняется на
настоящих данных.

- Правка **не уходит в базу по Enter**: она копится в буфере, изменённые ячейки подсвечены.
- **«Применить»** сначала показывает готовые `UPDATE … WHERE ключ` и только после подтверждения
  выполняет их **одной транзакцией**: половина применённых правок хуже, чем ни одной.
- Отказ называется причиной: нет ключа в выборке, ключ пуст (`= NULL` не найдёт ничего), столбец
  сам входит в ключ, подключение помечено `"readOnly": true`.
- Очистка ячейки пишет `NULL`, пустая строка остаётся пустой строкой, двоичное не правится.
- После применения запрос перечитывается: база могла изменить значение по-своему (тип, триггер,
  регистр), и показывать набранное вместо сохранённого — врать в глаза.

**`"readOnly": true` — способ защитить боевую базу настройкой, а не вниманием.** Осторожность
должна быть свойством подключения, а не свойством человека в конкретную минуту.

## Подсказки по схеме

**Ctrl+Space в консоли.** После `FROM`/`JOIN`/`UPDATE`/`INTO` предлагаются таблицы, в
`SELECT`/`WHERE`/`ON`/`SET` — столбцы упомянутых в запросе таблиц, а `u.` сужает список до таблицы
за псевдонимом (`FROM users u`).

Схема берётся из уже прочитанного дерева: подсказка **не ходит в базу по нажатию клавиши**.
Столбцы таблицы, которую не разворачивали, дочитываются один раз в фоне.

## Пределы, названные вслух
- Выборка ограничена 200 строками — предел ставится и в тексте запроса, и на стороне драйвера
  (`setMaxRows`), поэтому миллион строк не приедет в память, даже если запрос написан руками.
  Свой `LIMIT` человека не подменяется.
- Таймаут запроса — 30 секунд.
- Разбор SQL знает строки, комментарии и долларовые кавычки PostgreSQL, поэтому `CREATE FUNCTION`
  не разъезжается на середине. Но это разбиение на операторы, а не разбор SQL: подсветки и
  автодополнения по схеме пока нет.
