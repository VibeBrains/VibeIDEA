# Спека: дежурные проверки (`.vibe/patrols.json`)

> Скопируйте этот файл целиком своей LLM и попросите: «собери мне `.vibe/patrols.json` для моего
> проекта» — этого документа достаточно, в исходники лезть не нужно.

## Что это и зачем

Любой ход агента начинается с модели, то есть с денег, — даже когда делать нечего. Дежурная
проверка переворачивает порядок: по расписанию запускается **дешёвая команда проекта**, и модель
зовётся, только если команда нашла повод. Большинство циклов при этом стоят ноль.

Форма подсмотрена у чужого работающего примера: обход открытых pull request'ов каждые пятнадцать
минут, где агента зовут только при конкретной находке.

## Файл

```jsonc
{
  "version": 1,
  "patrols": [
    {
      "id": "todo",                       // обязателен, уникален в файле
      "label": "Незакрытые TODO",         // необязательно; без него зовётся по id
      "probe": "! grep -rq TODO src",     // обязателен: команда-проба
      "everyMinutes": 30,                 // 1…1440, по умолчанию 15
      "prompt": "Разбери свежие TODO",    // что предложить агенту; без него — только сообщить
      "maxPerDay": 3,                     // сколько раз в сутки беспокоить; по умолчанию 12
      "active": true                      // запись без поля активна
    },
    { "id": "ci", "probe": "gh run list --json conclusion | grep -q failure",
      "prompt": "Посмотри, почему упал последний прогон CI" }
  ]
}
```

## Общий набор: поля `active` и `products`

Файлы `.vibe` приезжают из **общего набора**, который пишут несколько продуктов сразу — VibeIDE, VibeIDEA, дальше VibeCLI. Поэтому у записи есть два необязательных поля, отвечающих на **разные** вопросы: `active` — «включено ли», `products` — «кому адресовано». Запись бывает вашей и выключенной, и чужой и включённой у соседа.

| Поле | Значение |
|---|---|
| `active` | Включена ли запись. Поля нет — включена. `false` — запись описана и лежит на виду, но не работает. Именно так едут готовые образцы в засеянных файлах: сид — рабочий файл, а не двойник рядом с рабочим |
| `products` | Кому запись адресована: массив стабильных id в нижнем регистре — `vibeide`, `vibeidea`, `vibecli`. Поля нет — запись **для всех**, и это верно почти всегда |

На что можно рассчитывать:

- **Выключенная запись не проверяется вообще.** Она не выполнится, поэтому VibeIDEA молчит о её содержимом — не жалуется ни на незнакомое значение, ни на отсутствующую обязательную строку. Исключение одно: находки безопасности (пароль в `dataSources.json`) называются вслух и у выключенной записи — пароль уже лежит в репозитории, и выключенность записи его оттуда не убирает.
- **Запись не для этого продукта пропускается молча.** Это не ошибка и не предупреждение.
- **Незнакомый id продукта — тоже молча мимо.** Сборка, выпущенная сегодня, увидит запись для продукта, которого ещё нет, и промолчит.
- **`products` не защищает от старых сборок.** Сборка, которая о поле ещё не знает, игнорирует его и запись выполняет. Поэтому запись, которая пока не должна работать везде, едет выключенной — адрес и выключатель работают вместе, а не вместо друг друга.

```jsonc
// Запись, адресованная одному продукту и пока выключенная.
{ "products": ["vibeidea"], "active": false /* … остальные поля записи … */ }
```

## Правила

- **Код возврата пробы и есть решение: `0` — делать нечего**, ненулевой — есть повод. То же
  правило, что у `skipIf` в [спеке дев-стека](serversSpec.md): одно правило на продукт лучше двух
  похожих.
- **Проба, которая не смогла запуститься, поводом не считается.** Иначе сломанная команда дёргала
  бы человека каждые пятнадцать минут.
- **Модель сама не зовётся.** Проверка приносит повод уведомлением, а кнопка «Отдать агенту»
  запускает ход по вашему нажатию. Фоновой расход, о котором узнают из счёта, хуже отсутствующей
  возможности.
- **Причина срабатывания пишется в журнал аудита** (какая проба, с каким кодом): проверка, о
  которой нельзя спросить «почему она сработала», через неделю выключается целиком.
- Интервал вне рамок 1…1440 — **отказ**, а не приведение к границе: «каждые ноль минут» человек
  написал не случайно, и подменять это своим значением значит делать не то.
- Битая запись пропускается с названной причиной, остальные работают. Нет файла — нет дежурства.
- Проба выполняется в корне проекта, таймаут 30 секунд.

## Чего здесь нет

- Расписания вида cron: интервал в минутах покрывает то, ради чего это заводится, а cron требует
  своего разбора и своих ошибок.
- Условий сложнее кода возврата. Правило, которое само нуждается в модели, не спасает ни от чего.

## Как проверить, что проба работает

Действие **«Дежурные проверки: прогнать сейчас»** (Help → Find Action) разбирает файл и немедленно
выполняет все включённые пробы: сколько записей прочиталось, что в них не так и какие сработали.
Без него первую настройку проверяют ожиданием — написал запись, подождал пятнадцать минут, ничего
не пришло, и непонятно, проба молчит или файл вовсе не читается.

Расписание при этом **не сбрасывается**: ручной прогон отвечает на вопрос «работает ли моя проба»,
а не подменяет дежурство. Строка «Дежурные проверки» есть и в отчёте диагностики: она отличает
«файла нет» от «файл есть, но записи битые» — молчат они одинаково.
