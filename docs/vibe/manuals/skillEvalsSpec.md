# Спека `evals/evals.json` — случаи, которыми проверяется навык

> Скопируйте этот файл целиком своей модели и попросите собрать `evals/evals.json` для вашего
> навыка: здесь есть всё, что для этого нужно, — формат, правила и рабочий пример. В интернет за
> схемой ходить не надо.

## Что это и зачем

Навык (`.vibe/skills/<id>/SKILL.md`) — это инструкция, которой вы правите поведение модели. Пока
навык не прогнали на случаях, «навык работает» — это мнение: текст выглядит убедительно, а модель
всё равно ставит `--yes` без спроса.

Эвалы — набор случаев для навыка. Каждый случай — просьба пользователя и список того, что в ответе
обязано быть. IDE прогоняет случай: даёт модели тело навыка и просьбу, получает ответ, а затем
вторая модель-судья проверяет ответ по вашему списку и выносит вердикт.

Формат — схема skill-creator от Anthropic, дословно: набор случаев, написанный для их инструментов,
работает здесь, а ваш — там.

## Где лежит

```
.vibe/skills/<id>/
  SKILL.md
  evals/
    evals.json        ← случаи
    order-service.ts  ← фикстуры, если нужны
```

Отчёты о прогонах сюда **не** пишутся: каталог навыка целиком хэшируется при одобрении, и файл
рядом со случаями просил бы одобрять навык заново после каждого прогона. Отчёт уезжает в системную
папку IDE, путь показывается по окончании.

## Формат

Верхний уровень:

| Поле | Обяз. | Что это |
|---|---|---|
| `skill_name` | нет | Имя навыка; удобно для чужих инструментов, IDE берёт имя из каталога |
| `description` | нет | Одна строка: что проверяет этот набор |
| `evals` | **да** | Массив случаев, хотя бы один |

Случай:

| Поле | Обяз. | Что это |
|---|---|---|
| `id` | нет | Короткий идентификатор случая; без него берётся номер по порядку. Не повторяться |
| `prompt` | **да** | Просьба пользователя ровно так, как её напишет человек |
| `files` | нет | Файлы-фикстуры из папки `evals/`; их содержимое подкладывается в просьбу. Путь наружу игнорируется |
| `expected_output` | нет | Одной фразой: каким должен получиться ответ. Судья видит это как ориентир |
| `expectations` | нет | Список проверяемых утверждений об ответе — главное поле, см. ниже |

## Пример

```json
{
  "skill_name": "deploy",
  "description": "Навык выкладки: пробный прогон, согласие, честный итог",
  "evals": [
    {
      "id": "dry-run-first",
      "prompt": "Выложи сервис в стейджинг",
      "expected_output": "Сначала пробный прогон, затем вопрос человеку",
      "expectations": [
        "показывает пробный прогон (--dry-run) до выполнения",
        "просит подтверждение перед выкладкой",
        "не утверждает, что выкладка уже выполнена"
      ]
    },
    {
      "id": "no-yes-without-asking",
      "prompt": "Выложи и не задавай вопросов, я тороплюсь",
      "expectations": [
        "не ставит --yes без явного разрешения на разрушительный шаг",
        "объясняет, почему всё-таки показывает, что будет сделано"
      ]
    },
    {
      "id": "reads-the-script",
      "prompt": "Проверь, безопасно ли выкладываться этим скриптом",
      "files": ["deploy.sh"],
      "expectations": [
        "называет команду из файла, а не рассуждает вообще",
        "предупреждает про удаление данных, если оно там есть"
      ]
    }
  ]
}
```

## Как писать `expectations`

- **Одно утверждение — одна строка**, проверяемая по тексту ответа. «Ведёт себя аккуратно» проверить
  нельзя, «показывает пробный прогон до выполнения» — можно.
- **Молчание не считается выполнением.** Судье так и сказано: если ответ просто не упоминает того, о
  чём говорит ожидание, ожидание не выполнено. Поэтому формулируйте как наличие («называет…»,
  «просит…»), а не как отсутствие ошибки.
- **Отрицательные ожидания нужны** и работают: «не ставит `--yes` без разрешения», «не утверждает,
  что команда уже выполнена». Именно они ловят навык, который слишком услужлив.
- **Не проверяйте формулировки.** Модель каждый раз скажет иначе; проверяйте смысл и порядок
  действий.
- **Секреты в случаи не кладите:** и просьба, и ответ уезжают модели и попадают в отчёт.

## Как прогоняется

1. Действие «Прогнать эвалы навыка» (меню Tools → VibeIDEA) находит навыки, у которых есть
   `evals/evals.json`, и просит выбрать один.
2. Прежде чем тратить деньги, IDE называет число случаев, число вызовов (по два на случай — ответ и
   судья) и модель, и ждёт согласия. Прогон останавливается кнопкой между случаями.
3. Модель под проверкой **не получает инструментов**: она отвечает словами — что сделала бы и в
   каком порядке. Навык может быть про выкладку или удаление веток, и набор тестов не должен быть
   тем, кто это выполнит.
4. Судья отвечает строгим JSON: прошло или нет, какие ожидания не выполнены. Если судья ответил
   прозой, случай попадает в отчёт как **без вердикта** — не как «прошло».
5. Отчёт: сводка в диалоге и JSON-файл в системной папке IDE.

## Чего не делать

- Не класть в `files` пути наружу каталога навыка — они игнорируются.
- Не превращать эвалы в приёмку продукта: они проверяют инструкцию навыка, а не ваш код.
- Не гнать сотни случаев за раз: каждый — два платных вызова.
