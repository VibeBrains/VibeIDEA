# Спека: пайплайны (`.vibe/pipelines.json`)

> Скопируйте этот файл целиком своей LLM и попросите: «собери мне `.vibe/pipelines.json` для …» — этого документа достаточно.

## Что это

Линейные цепочки шагов-ролей для панели Vibe Agent (кнопка «Пайплайн…»). Каждый шаг — отдельный промпт агенту с ролью, задачей и артефактами предыдущих шагов. Контракт совместим с VibeIDE.

## Формат

```jsonc
{
  "version": 1,
  "pipelines": [
    {
      "id": "feature",                    // обязателен, уникален; по нему запуск
      "name": "Фича под ключ",
      "description": "Спроектировать, реализовать, проверить",
      "steps": [                          // 1..20 шагов, порядок = порядок выполнения
        { "role": "planner",       "task": "Разбей задачу на шаги и запиши план в docs/plan.md" },
        { "role": "backend-dev",   "task": "Реализуй по плану", "acceptance": "Проект собирается" },
        { "role": "code-reviewer", "task": "Найди дефекты в изменениях", "ignorePreviousArtifacts": true }
      ]
    }
  ]
}
```

Поля шага: `role` (обяз., из списка ниже), `task` (обяз.), `acceptance` (передаётся агенту дословно), `maxTokens`/`maxSteps` (пока не применяются — см. отличия), `continueOnFailure` (выполнять даже после провала предыдущего), `ignorePreviousArtifacts` (шаг не получает ни путей, ни резюме — «свежий взгляд» для проверяющего), `provider` + `model` (шаг идёт к этой модели напрямую, минуя ACP-агента), `escalation` (шаг нужен, только если гейт не принял предыдущий).

## Шаг на своей модели и каскад

`provider` и `model` уводят шаг с ACP-агента на **прямой запрос к модели**. У такого шага **нет
инструментов и нет доступа к файлам** — он получает текст (роль, задача, приёмка, итог прошлого
шага) и отвечает текстом. Поэтому он разрешён только ролям, которые и так ничего не пишут
(`explore`, `planner`, `code-reviewer`, `qa`, `security`, `critic`); пишущая роль с `model`
отвергается при загрузке, а не молча превращает «реализуй» в «расскажи, как реализовать».
Половина пары (только `provider` или только `model`) — тоже ошибка загрузки.

Так описывается **каскад**: дешёвая модель делает черновик, а дорогая работает не всегда. Решает
это гейт — хук `pipelineStepEnd` в `.vibe/hooks.json`: его код выхода `0` значит «черновик принят»,
и шаги с `"escalation": true` пропускаются; код `2` — «не принят», и они выполняются. **Без гейта
поле `escalation` не значит ничего**: непроверенный черновик принимать нечем, и шаг выполняется.

Экономия считается честно: доля прогонов, где гейт принял, умноженная на разницу цен, **минус**
повторная подача контекста дорогому шагу. Последнее в бенчмарочных формулах обычно пропущено, а в
счёте — нет.

Роль `critic` существует ради второй половины той же идеи: замечания стоит спрашивать у модели
**другого семейства**, потому что своей ошибки модель не видит по той же причине, по которой её
сделала. Это инженерная эвристика (декорреляция ошибок), а не измеренный факт — источники, которые
её заявляют, данных не приводят.

## Роли (закрытый список)

`explore · implement-step · recover-or-skip · orchestrator · planner · designer · frontend-dev · backend-dev · code-reviewer · qa · security`

Неизвестная роль — ошибка записи со списком доступных, а не агент, молча выдающий прозу.

## Передача между шагами

Следующий шаг получает **пути файлов**, которых касались предыдущие шаги (пути накапливаются), и **резюме последнего шага** (хвост его ответа, ≤2000 символов). Содержимое файлов не вставляется — агент читает нужное сам.

## Провал

По умолчанию провал шага (ошибка вызова агента) останавливает пайплайн; оставшиеся шаги печатаются как «пропущен» — видно, почему хвост не выполнялся. `continueOnFailure: true` ставится вручную на действительно независимый шаг.

## Устойчивость

JSONC (комментарии, висячие запятые). Сломанный пайплайн (без id, пустые steps, дубль id — вторая запись, шаг без role/task, >20 шагов) пропускается с предупреждением **до** списка; остальные работают.

## Отличия от VibeIDE (честные границы)

- **Роль не ограничивает инструменты физически**: у VibeIDE роли-субагенты имеют список разрешённых инструментов; у нас ACP-агент владеет своими инструментами сам — read-only роли получают жёсткую инструкцию «не изменяй файлы», а записи по-прежнему проходят через permission-диалоги.
- `maxTokens`/`maxSteps` парсятся, но пока не пробрасываются агенту (у ACP нет стандартного поля бюджета).
- Провал = ошибка вызова; машинной проверки `acceptance` нет (и у VibeIDE не заявлена).
