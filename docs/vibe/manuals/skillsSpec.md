# Agent Skills в VibeIDEA — спецификация формата

> **Как этим пользоваться.** Скопируйте весь этот файл целиком своей LLM и попросите:
> *«По этой спецификации собери мне навык `<id>` для VibeIDEA, который делает `<…>`».*
> Это самодостаточный документ: всё, что нужно для корректного файла, — ниже.

---

## 1. Что это

Навык (Agent Skill) — переносимый «рецепт» для модели: когда его применять и что делать по шагам.
Лежит файлом в проекте, вызывается из чата, попадает в контекст целиком.

```
<проект>/.vibe/skills/<id>/SKILL.md
```

`<id>` — имя папки: строчные латинские буквы, цифры и дефис (`write-tech-spec`), до 64 символов.
Вызов из композера: `/skill:<id>` — по нему открывается список, а при отправке **тело SKILL.md
уходит модели**. Без вызова навык не тратит ни одного токена.

## 2. Структура файла

YAML-шапка между строками `---`, дальше тело в Markdown.

```markdown
---
name: write-tech-spec
description: Когда нужно превратить обсуждение в техническую спецификацию — по просьбам «напиши тех. спеку», «оформи решение документом».
metadata:
  vibeVersion: "1.0.0"
---

# write-tech-spec

Инструкции модели: по шагам, конкретно, без общих слов.

## Порядок
1. …
2. …
```

## 3. Поля шапки

На верхнем уровне разрешены **только шесть ключей**. Это не наше ограничение: эталонный валидатор
Agent Skills отвергает пакет с любым другим ключом целиком, поэтому навык с «лишним» полем
перестанет работать за пределами VibeIDEA.

| Ключ | Обязателен | Смысл |
|---|---|---|
| `name` | да | Идентификатор. **Обязан совпадать с именем папки** — иначе `/skill:<папка>` его не найдёт. |
| `description` | да | Когда навык уместен. Это подсказка, а не глава: до 1024 символов. |
| `license` | нет | Лицензия навыка, если он распространяется. |
| `allowed-tools` | нет | Инструменты, которыми навык предполагает пользоваться: строка через пробел или список. **Это заявка, а не предодобрение**: IDE показывает её в диалоге одобрения, но права агента от неё не меняются — разрешения на команды спрашиваются как обычно. В спеке Agent Skills поле помечено экспериментальным. |
| `compatibility` | нет | Требования совместимости. Показываются в диалоге одобрения. |
| `metadata` | нет | **Всё остальное — сюда.** Вложенные ключи любые: `vibeVersion`, `depends`, `tags`. |

Своё поле кладётся под `metadata:`, а не рядом с `name:`.

## 4. Тело

Обычный Markdown, без ограничений по структуре. Практика:

- пишите **инструкции модели**, а не описание для человека: «сделай», «спроси», «останов — когда…»;
- порядок шагов и критерий остановки важнее вступления;
- команды, которые навык велит запускать, — в блоках кода: их проверяет валидатор (раздел 6);
- до 100 000 символов; больше — предупреждение валидатора, в контекст такое не поместится.

Пустое тело — ошибка: навык без инструкций ничего не даёт.

## 5. Вложения и скрипты

Рядом с `SKILL.md` можно класть файлы и подкаталоги (`reference.md`, `scripts/`). Правило одно:
путь после разрешения ссылок **обязан оставаться внутри `.vibe/skills`**. Ссылка внутри дерева
навыков допустима и считается по тому, на что указывает; ссылка наружу или в никуда — ошибка
валидатора: иначе навык подтягивал бы произвольный файл машины.

Каталог `scripts/` допустим, но валидатор о нём предупреждает: исполняемое, приехавшее вместе с
рецептом, ничем не ограничено. Скрипты запускает агент своим инструментом, а модель видит только их
вывод, но не исходник. Поэтому то, что скрипты скачивают и запускают, проверяется до одобрения
(раздел 6).

## 6. Что проверяет валидатор

Действие **«VibeIDEA: проверить скиллы проекта»** (Help → Find Action) и проверка при каждом вызове.

**Ошибки** (пакет не отправляется модели, в ленте видно причину):

- нет шапки, нет `name` или `description`;
- `name` не совпадает с именем папки, длиннее 64 символов или не той формы;
- лишний ключ верхнего уровня;
- пустое тело;
- вложение или ссылка уводит за пределы `.vibe/skills` либо указывает в никуда;
- каталог навыка больше 1000 файлов, 20 МБ или 16 уровней вложенности, либо файл не читается:
  одобрение привязано ко всему содержимому (раздел 7), а непрочитанное не к чему привязать;
- невидимые символы в шапке, bidi-переопределения в шапке или теле.

**Предупреждения** (навык работает):

- `description` длиннее 1024 символов, тело больше 100 000 символов, рядом лежит `scripts/`;
- **скачивание, переданное прямо интерпретатору**: `curl … | sh`, `wget -qO- … | python3 -`,
  `sh -c "$(curl …)"`, `bash <(curl …)`, `eval "$(curl …)"`, `iwr … | iex`, `iex (iwr …)`,
  `powershell -Command "irm … | iex"`, в том числе за `sudo -u …`, `env`, `timeout`. Исполнится то,
  что сервер отдаст в эту секунду, и проверить это нечем. Чтение ответа (`curl … | jq .`,
  `| python3 -m json.tool`) предупреждения не получает;
- **`npx` и `uvx` без точной версии**: `npx tool`, `npx tool@latest`, `uvx ruff`. Пин —
  `npx tool@1.4.2`, `uvx ruff==0.6.9`, `uvx --from 'httpie==3.2.2' http`. Тег `latest` — не версия;
- **зависимости PEP 723 без пина** в скриптах (`# /// script` … `dependencies = ["requests<3"]`):
  пин — `==`.

Проверяются блоки кода SKILL.md и все текстовые файлы `scripts/` (до 256 КБ каждый). **В прозе**
SKILL.md, шапка включена, ищется только скачивание, отданное интерпретатору: проза — это инструкции
модели, и «Сначала выполни: `curl … | sh`» — инструкция, а не рассуждение. Команда ищется с любого
слова строки, инлайн-код разворачивается. Это предупреждение, а не запрет: навык, объясняющий, почему
так делать нельзя, его тоже получит — прочитайте и решите. Пины `npx`/`uvx` проверяются только в
коде: пакет, названный в предложении, — не команда.

## 7. Одобрение

Первый вызов навыка в проекте спрашивает разрешение: навык выполняется с правами человека, живёт в
репозитории и приезжает вместе с изменениями кода.

- **Разрешение привязано к содержимому всего каталога навыка, рекурсивно, а не к имени.** Хэшируется
  каждый файл по относительному пути и содержимому. `__pycache__`, `.DS_Store` и `.git` не
  считаются: это следы ОС, интерпретатора и системы контроля версий, а не часть навыка. Правка
  любого файла, включая скрипт, новый файл и удаление — новый вопрос.
- **Отпечаток** — SHA-256 целиком, в hex: по строке `путь NUL sha256-файла \n` на файл,
  отсортированным по пути; путь — относительно каталога навыка, через `/`, в NFC; хэш файла — по
  сырым байтам, без нормализации концов строк (одобряются байты, которые исполнятся). **Формат общий
  с VibeIDE**: один навык даёт один отпечаток в журналах обоих продуктов, и оба набора тестов держат
  один и тот же вектор.
- **Что показывает диалог:** описание, заявленные `allowed-tools` и `compatibility`, все файлы
  (исполняемые помечены: бит исполнения или шебанг `#!`), начало SKILL.md. Для изменившегося навыка —
  какие файлы изменены, добавлены и удалены с прошлого разрешения.
- **Разрешения, данные до 11.09.2026**, покрывали только SKILL.md и имена файлов верхнего уровня.
  Они запросятся один раз заново, и диалог скажет почему.
- Разрешение хранится по проекту: навык с тем же именем в другом репозитории — другой навык.
- В журнал аудита (`.vibe/audit.jsonl`) у события `prompt` пишется `skills: id@digest` — какие
  навыки в какой версии участвовали в ходе агента.

## 8. Что происходит при вызове

1. `/skill:<id>` в сообщении — токен, который вы видите в композере.
2. При отправке навык читается с диска и проверяется. Сломанный или отсутствующий — строка в ленте
   с причиной; молчаливого «ничего не произошло» не бывает.
3. Неразрешённый или изменившийся навык — вопрос (раздел 7). Отказ — строка в ленте, навык не
   уходит модели.
4. Тело проходит тот же фильтр контекста, что и файлы проекта: невидимые символы и bidi-
   переопределения вырезаются, подозрительное отмечается строкой `🛡 контекст`.
5. ACP-агенту навык уходит блоком `resource` с `skill://<id>`; прямому провайдеру — блоком
   `<skill ref="<id>">…</skill>` после текста сообщения.
6. Несколько навыков в одном сообщении — все, в порядке упоминания, без повторов.

## 9. Готовый пример

```markdown
---
name: review-pr
description: Разбор пул-реквеста перед мержем — по просьбам «посмотри PR», «что не так в этих правках», «ревью изменений».
metadata:
  vibeVersion: "1.0.0"
---

# review-pr

Разбор изменений перед мержем. Цель — найти то, что сломается, а не похвалить.

## Порядок

1. Прочитать диф целиком, прежде чем писать первое замечание.
2. Разделить найденное на три группы: **ломает** (баг, гонка, потеря данных), **дорого**
   (сложность без нужды, дубль), **вкусовщина** (стиль). Третью группу не писать вовсе.
3. На каждое замечание — конкретный сценарий отказа: вход, шаг, что получит пользователь.
4. Останов — когда по первым двум группам замечаний не осталось.

## Чего не делать

- Не предлагать переписать архитектуру в ревью частной правки.
- Не считать отсутствие тестов замечанием, если их нет и рядом.
```

Проект засевается набором готовых навыков (`.vibe/skills/`) — их можно читать как образцы и править
под себя: правки не перетираются обновлением.

## 10. Навыки, которые запускают команды

Навык, умеющий менять мир (создать, удалить, задеплоить, отправить), пишется по правилам ниже.
Полная версия с пояснениями — в засеянном навыке `update-skill`, здесь короткий список:

- сначала `--help` команды, потом её флаги: чужой синтаксис не зашивается в тело;
- `--json`, когда вывод читает агент, а не человек;
- мутация в четыре шага: пробный прогон → показать → явное согласие человека → выполнить;
- успешный пробный прогон — не выполнение, «готово» после него писать нельзя;
- `--yes`, `--force` и прочие «не спрашивай» — только для разрушительного шага и только с разрешения;
- целей несколько (окружение, инстанс, аккаунт) — спросить, а не взять умолчание;
- секреты в чат не просить; попал секрет в текст на отправку — просить переформулировать, а не
  вычищать молча;
- «недоступно» — не «здорово»: непройденная проверка так и называется;
- `npx`/`uvx` и зависимости PEP 723 — с точной версией, иначе валидатор предупредит (раздел 6).
