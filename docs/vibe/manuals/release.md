# Как выпустить релиз

Порядок проверен на v0.1.0 (31.08.2026). Каждый шаг заканчивается фактом, а не намерением: если
шаг нечем подтвердить, релиз не готов.

## Две фазы и стоп между ними

Механика перенята у VibeIDE (04.09.2026) после выпуска 0.4.0, который ушёл в мир, не побывав в
руках владельца: «я бы 0.4.0 ни за что не выпустил, там БД только на просмотр».

| Фаза | Команда владельца | Что делает агент | Чем кончается |
|---|---|---|---|
| **1. Сборка** | «собери», «билд» | бамп версии → гейты и тесты → сборка → гейт дистрибутива → канал обновлений → **штамп** | артефакт отдан владельцу, **СТОП** |
| **2. Публикация** | «публикуй», «релиз» | заметки → тег → публикация тех же артефактов | релиз на GitHub |

**Фаза 2 не начинается без явного «гуд» от владельца после того, как он сам пощупал сборку.**
Не «он не возражал», не «прошло время», не «гейты зелёные» — явное слово. Фаза 1 запускается тоже
по команде, ничего не собирается само.

**Не прошла проверку в руках** — правим, поднимаем версию заново и снова Фаза 1. Забампованная,
но не выпущенная версия — нормальное состояние: её заметки вливаются в следующий выпуск
(в v0.3.1 это уже случалось, и `releaseChangelog.sh` называет такие теги отдельным списком).

## 1. Ветка

Повседневная работа идёт в `next`. Релиз — осознанное «выпускаем»: `main` догоняет `next`, и только
после этого ставится тег. Обратный порядок означал бы тег на том, что ещё может измениться.

```bash
git checkout main && git merge --ff-only next
```

## 1б. Поднять версию продукта

`vibeidea-customization/resources/idea/VibeIdeaApplicationInfo.xml`, атрибуты `major`/`minor`/`micro` —
это то, что человек увидит в «О программе» и назовёт в issue. Номер платформы (`VI-263.*`) не
трогаем: он отдельно, по нему считается совместимость плагинов.

Забыть невозможно: `releaseStamp.sh` сверяет эту версию с выпускаемым тегом и отказывается
штамповать при расхождении — установленная сборка, называющая себя чужим номером, отравляет каждый
последующий баг-репорт.

## 2. Собрать и проверить дистрибутив

```bash
sh vibe-plugins/deps/download.sh      # LSP4IJ и языковые серверы по закреплённым версиям
./vibeidea-installers.cmd -Dintellij.build.target.os=current -Dintellij.build.target.arch=current
./vibe-plugins/tools/checkVibeDist.sh
```

Гейт дистрибутива обязателен: он проверяет то, чего не видит ни один юнит-тест — вписан ли готовый
плагин в индекс, доехали ли библиотеки внутрь плагина, **запускаются** ли встроенные серверы. За
один день 31.08.2026 четыре дефекта нашлись только здесь
([разбор](../knowledge/build/bundledPluginIndex.md)).

Перед сборкой — четыре гейта исходников и тесты, иначе выпускается непроверенное.

### Вторая ОС: Windows

Релиз одной версии собирается по одной сборке на ОС, и каждая делается на своей машине. Windows-
сборка даёт два артефакта — инсталлятор `vibeIdea-<build>.exe` и архив `vibeIdea-<build>.win.zip`;
гейт дистрибутива открывает zip. Сравнение exe с zip сборка в dev-режиме **пропускает**, поэтому
инсталлятор проверяется тихой установкой во временный каталог и сравнением с распакованным zip:

```bash
sed 's/^launcher64=1/launcher64=0/' platform/build-scripts/resources/win/nsis/silent.config > /tmp/silent.config
out/vibeidea/artifacts/vibeIdea-*.exe /S /CONFIG=$(cygpath -w /tmp/silent.config) /D=D:\vi-test
diff -rq D:/vi-test <распакованный zip> | grep -v Uninstall   # пусто = совпадают
D:/vi-test/bin/Uninstall.exe /S                                # снять запись из «Программ»
```

Каталог установки для проверки — **короткий**: генератор NSIS включает обход MAX_PATH только для
путей, которые считает длинными при типичном каталоге установки (~113 символов); в каталог длиннее
файлы теряются молча ([разбор](../knowledge/build/windowsBuild.md)).

Те же команды, что выше, из Git Bash; отличия — в подготовке машины и клона
([разбор](../knowledge/build/windowsBuild.md)):

```bash
git submodule update --init                 # сиды .vibe: pull двигает указатель, но не рабочую копию
git config core.longpaths true              # без этого чекаут обрывается на путях длиннее 260
git clone --shallow-since=<дата синка минус 3 дня> https://github.com/JetBrains/android.git android
git -C android checkout "$(git -C android log --before='<дата коммита синка>' -1 --format=%H origin/master)"
python vibe-plugins/tools/makeWinImages.py  # только если менялся vibeidea.icns: ico и картинки NSIS
```

Нужны `python`, `node`, `php` на PATH (гейт дистрибутива запускает встроенные серверы), `gh`.

**Тег уже стоит** — его поставила первая ОС. Если Windows-сборке понадобились правки упаковки
(иконка, картинки инсталлятора, скрипты гейтов), сборка делается на **упаковочном потомке тега**:
штамп и публикация принимают коммит, который является потомком тега и отличается от него только
в `build/`, `vibeidea-customization/`, `vibe-plugins/tools/`, `docs/`, `updates/` и корневых `*.md`
(`releasePackagingOnly.sh`; список изменённых файлов печатается — прочитать его). Любой файл вне
этого — продукт изменился, и это следующая версия, а не второй артефакт этой. Переставлять
опубликованный тег нельзя: скачанное по нему перестанет с ним совпадать.

**Исключение: правка продукта ради работоспособности этой ОС.** Бывает, что вторая ОС при сборке
обнаруживает: обещанное в этом релизе на ней не работает вовсе. Тогда выбор — из двух зол:
артефакты одной версии слегка разойдутся, либо на второй ОС уедет молча неработающее обещание.
Второе хуже, поэтому выход есть, но он обязан быть **названным**:

```bash
./vibe-plugins/tools/releaseStamp.sh vX.Y.Z --product-fix "что и почему одной строкой"
```

Причина уходит в `release-stamp.json`, публикация печатает её отдельной строкой «ВНИМАНИЕ», а список
изменённых файлов продукта выводится целиком. Смена закреплённых версий серверов (`pins.env`,
`download.sh`) не проходит **и так**: это уже другой состав поставки, а не правка. Само расхождение
описывается в заметках релиза — человек, читающий страницу выпуска, должен узнать о нём оттуда, а не
из различия в поведении. Прецедент — v0.4.0 (04.09.2026): «PHP на Windows заработал» не работал на
Windows, лаунчер Phpactor уехал в Windows-артефакты поверх тега.

Публикация на существующий релиз (`releasePublish.sh`) доливает файлы и приводит текст релиза к
файлу заметок — поэтому раздел «Установка» в заметках дополняется Windows-блоком **до** публикации,
вместе с sha256 обоих файлов. Ассет с тем же именем уже в релизе — отказ.

## 2в. Подпись (когда появятся учётки)

Сборка сейчас **не подписана** ни на macOS, ни на Windows, и это единственная причина, по которой
Gatekeeper показывает «Файл не может быть открыт», SmartScreen — «Windows защитила ваш компьютер», а
Касперский удалил `idea64.exe` по поведению. Всё остальное для подписи готово и лежит в репозитории;
не хватает **учёток**, которые может завести только владелец:

| ОС | что купить | куда положить | что запустить |
|---|---|---|---|
| macOS | Apple Developer Program → сертификат «Developer ID Application»; профиль `xcrun notarytool store-credentials vibeidea …` | сертификат — в связку ключей; `VIBE_MAC_SIGN_IDENTITY`, `VIBE_NOTARY_PROFILE` — в окружение | `./vibe-plugins/tools/signMac.sh` |
| Windows | сертификат подписи кода (OV/EV) **или** Azure Trusted Signing | `VIBE_WIN_SIGN_THUMBPRINT` либо `VIBE_WIN_SIGN_DLIB` + `VIBE_WIN_SIGN_METADATA`; `signtool` из Windows SDK | `.\vibe-plugins\tools\signWindows.ps1` |

Оба скрипта работают **после сборки и до штампа** и без учётки останавливаются первой строкой,
объясняя, чего нет — молча выпустить неподписанный файл они не могут. `--dry-run` / `-DryRun`
перечисляет, что было бы подписано. Подписывается распакованное приложение (Gatekeeper проверяет
`.app`, а не образ), образ пересобирается, нотаризуется и получает пришитый билет; на Windows — оба
лаунчера, все `exe`/`dll` архива и инсталлятор, с меткой времени (без неё подпись умирает вместе с
сертификатом). Подписанные файлы кладутся рядом с оригиналами — публиковать именно их, а хеши в
заметках снимать с них же.

Почему не внутри сборки платформы: её путь подписи (`SignTool`) рассчитан на инфраструктуру вендора —
отдельную машину подписи с её протоколом. Для одного человека с одним Mac честный путь — штатные
инструменты Apple и Microsoft поверх готового образа.

## 3. Заметки

**Фраза поддержки — обязательная часть заметок, а не украшение.** Порядок и база — в
[releaseDonationPhrases.md](../releaseDonationPhrases.md): предложить варианты из «Активных»,
при необходимости сочинить новые, **спросить владельца**, записать выбранное в историю и убрать из
«Активных». Самовольно в файл не писать.

Проверяется гейтом, а не памятью (перенято у VibeIDE):

```bash
./vibe-plugins/tools/checkVibeReleaseNotes.sh vX.Y.Z docs/vibe/references/releaseNotes-vX.Y.Z.md
```

Он падает на пропущенной подписи, на пустой строке между вступлением и подписью, на подписи, не
записанной в историю, на относительной ссылке QR и на забытой заготовке `__SHA256__`. Его же
вызывает `releasePublish.sh` первым делом: узнавать о пропущенной фразе после заливки 800 МБ —
поздно. Повод завести гейт — выпуск 0.4.0, где шаг с фразой был пропущен молча.


Черновик — от последнего **опубликованного** релиза, а не от последнего тега:

```bash
./vibe-plugins/tools/releaseChangelog.sh vX.Y.Z
```

Разница существенна ровно тогда, когда тег поставили, а выпуск отложили: версия есть в git и
отсутствует на странице релизов, и заметки, отсчитанные от неё, молча теряют всё, что в неё
входило. Скрипт берёт базлайн у GitHub и отдельным списком называет неопубликованные версионные
теги в диапазоне — их содержимое обязано войти в текущие заметки. Чужие коммиты синка отфильтрованы:
состав продукта определяет наш код.

Вывод — сырьё, а не заметки. Заметки пишутся о том, что человек почувствует.

Оформление — правило, а не вкус: разделы с эмодзи и живым заголовком, жирный зачин плюс проза,
точные шаги обхода неподписанной сборки, отдельный раздел «чего пока нет», блок поддержки. Подробно
— [agentsGuide.md, раздел 9](../agentsGuide.md), образец —
[releaseNotes-v0.1.0.md](../references/releaseNotes-v0.1.0.md).

Фраза поддержки берётся из пула [releaseDonationPhrases.md](../releaseDonationPhrases.md): выбранная
переезжает в «Историю использования» и удаляется из «Активных».

Контрольная сумма установщика идёт в заметки — скачавший должен иметь возможность проверить файл:

```bash
shasum -a 256 out/vibeidea/artifacts/vibeIdea-*-aarch64.dmg
```

## 3б. Канал обновлений

Установленная IDE спрашивает `updates/updates.xml` с ветки `main` (адрес — `VibeProductUrls`).
Файл пишется **по собранному артефакту**, а не по версии из головы: номер сборки берётся из
`product-info.json` рядом с dmg/zip, и отображение «версия → номер» живёт в одном месте
(`VibeBuildNumber` в сборке).

```bash
./vibe-plugins/tools/releaseUpdatesXml.sh vX.Y.Z
git add updates/updates.xml && git commit -m "release: канал обновлений X.Y.Z"
```

Коммит — **до штампа**: штамп сверяет файл с артефактом и откажет, если записи нет. Откажет он и
на номере сборки `SNAPSHOT`: платформа читает его как максимум, и такая сборка считала бы себя
новее всего, что мы когда-либо опубликуем. Патчей канал не несёт — обновление приходит как
уведомление со ссылкой на релиз; настройки при установке поверх сохраняются.

## 4. Штамп: что именно проверено

```bash
./vibe-plugins/tools/releaseStamp.sh vX.Y.Z
```

Штамп фиксирует версию, коммит, имя файла и его sha256 — и отказывается работать на грязном дереве.
Между «собрал и проверил» и «выложил» проходит время, и в него помещается ещё одна сборка или
правка; без штампа расхождение обнаруживает пользователь.

## 5. Тег и публикация

```bash
git tag -a vX.Y.Z -m "VibeIDEA X.Y.Z — короткая суть"    # на ТОТ коммит, который заштампован
git push origin main next vX.Y.Z
./vibe-plugins/tools/releasePublish.sh <файл-заметок> --dry-run   # сверка без публикации
./vibe-plugins/tools/releasePublish.sh <файл-заметок>             # создание релиза и загрузка
```

Фаза 2 сверяет sha256 файла, коммит `HEAD`, чистоту дерева и то, что тег указывает **на
заштампованный коммит**. Любое расхождение — отказ: «наверное, тот же файл» и есть то
предположение, ради проверки которого штамп существует.

Загрузка 800 МБ **не укладывается в лимит одной команды** (проверено на v0.2.0: релиз создался,
заливка ассета оборвалась по таймауту). Если это случилось — релиз уже есть, доливать файл
отдельно и в фоне:

```bash
gh release upload vX.Y.Z <файл> --repo VibeBrains/VibeIDEA --clobber
```

Проверить, что файл на месте:

```bash
gh release view vX.Y.Z --repo VibeBrains/VibeIDEA --json assets --jq '.assets[] | {name, size, state}'
```

`state: uploaded` — единственное подтверждение. «Команда не выдала ошибку» им не является.

## 6. После публикации

- QR в заметках открыть и убедиться, что картинка отдаётся: ссылка обязана быть **абсолютной**
  (`raw.githubusercontent.com`), относительные пути работают в README и не работают в теле релиза.
- Заметки сохранить в `docs/vibe/references/releaseNotes-vX.Y.Z.md` — следующий релиз равняется на
  предыдущий, а не вспоминает.
- Пункт в [roadmap.md](../roadmap.md) со ссылкой на релиз.

## Права и учётки

Публикация делается из-под учётки, у которой есть **admin** на репозитории. У личного репозитория
(`type: User`) админ ровно один — владелец; ролей для коллабораторов там не существует, и «поднять
роль до Admin» невозможно в принципе. Коллаборатор с правом записи может пушить, но не может менять
ветку по умолчанию, описание и темы.

Если `gh` авторизован под другой учёткой — вход через устройство, секрет при этом не проходит через
чужие руки:

```bash
gh auth login --hostname github.com --git-protocol https --web --scopes repo
```

## Первая публикация форка

Проверить `ls .git/shallow` **до** пуша. Поверхностный клон сервер не примет —
`index-pack failed`; лечится пересборкой корня, рецепт в
[shallowClonePush.md](../knowledge/gitAndTools/shallowClonePush.md).
