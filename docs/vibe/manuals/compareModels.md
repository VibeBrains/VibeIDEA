# Как сравнить две модели на своём репозитории

Мануал отвечает на вопрос «какая модель лучше **для нашего кода**». На вопрос «какая модель лучше
вообще» он не отвечает, и ниже сказано, почему такого ответа не существует в том виде, в каком его
обычно ищут.

## Почему не по бенчмаркам

Публичный процент меряет не модель, а **связку «модель + харнесс»**. Один и тот же Claude Opus 4.8
даёт 69,2 % на SWE-bench через собственный стенд Anthropic и 51,9 % на стандартизированном стенде
Scale AI SEAL — разрыв 17,3 пункта при одной и той же модели; у Gemini 3.1 Pro разброс между
постановками доходит до 26,4 пункта. Разбор и ссылки —
[references/digest20260831.md](../references/digest20260831.md), правило —
[knowledge/architecture/benchmarksMeasureHarness.md](../knowledge/architecture/benchmarksMeasureHarness.md).

Отсюда практическое следствие: сравнивать модели можно только **одним харнессом**, и единственный
харнесс, который у вас есть на руках, — VibeIDEA на вашем репозитории.

## Что понадобится

- Две цели в пикере моделей (провайдер + модель), обе с ключом.
- Задача, которая **повторяема**: результат можно измерить командой, а не глазом.
- Чистое дерево (`git status` пуст) — иначе второй прогон стартует с правок первого.

## Порядок

1. **Выберите метрику и направление ДО работы.**
   Settings → Tools → VibeIDEA → Агент: шаблон метрики и направление («меньше лучше» или «больше
   лучше»). Решать направление после прогонов — способ назвать регрессию успехом.

2. **Снимите базу.**
   ```
   /measure <команда, печатающая число>
   ```
   Первый запуск становится базой. Годится всё, что печатает число: время сборки, размер бандла,
   процент покрытия, число падающих тестов.

3. **Прогон первой модели.**
   Выберите цель, дайте задачу, дождитесь конца хода. Затем `/measure <та же команда>` — теперь в
   ответе есть сравнение с базой в процентах.

4. **Верните дерево в исходное состояние.**
   ```bash
   git stash -u && git stash drop
   ```
   Второй модели должна достаться та же начальная точка. Это самая частая ошибка в таком сравнении:
   вторая модель «дописывает» за первой и выглядит лучше или хуже без всякой связи со своим
   качеством.

5. **Прогон второй модели — той же задачей, слово в слово.**
   Переформулированная задача меряет уже формулировку, а не модель.

6. **Сравните не только метрику.** В сравнении участвуют три числа, и метрика — только одно из них:
   - **исход** — прогон закончился сам или упёрся (журнал прогонов, панель «Прогоны»);
   - **расход** — токены и деньги (действие «VibeIDEA: расход по ролям»);
   - **время** — сколько шёл ход.
   Модель, выигравшая процент метрики втрое дороже, не выиграла.

## Как записать результат

Сравнение имеет срок годности: провайдер меняет модель под тем же именем, а репозиторий меняется
сам. Поэтому в записи обязательны **дата, идентификаторы моделей и команда метрики** — без них через
месяц это будет число без смысла. Место записи — `docs/vibe/knowledge/`, если из сравнения вышел
вывод, влияющий на выбор по умолчанию.

Чего в записи быть не должно — **вендорских процентов**. Каталог особенностей моделей
(`ModelQuirks`) описывает, что модель принимает, а не насколько она хороша; чужой процент, попавший
в наш файл, читается как наше измерение и переживёт тот релиз, к которому относился.

## Чего этот способ не даёт

- **Статистики.** Два прогона — это два прогона, а не выборка. Разница в пределах нескольких
  процентов ничего не значит; интересны разы, а не проценты.
- **Переносимости.** Вывод верен для вашего репозитория и вашей задачи. Это не недостаток метода:
  именно на этом репозитории вам и работать.
