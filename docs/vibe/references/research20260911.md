## Поправки к исследованию 09.09

1. **`Origin` не проверяется.** В §3 записано, что `HttpApiPolicy` проверяет `Origin` и `Host` с
   ответом 403. На деле пункт, подписанный «Origin», проверяет адрес пира (`HttpApiPolicy.kt:91–93`), а
   заголовок `Origin` не читается нигде (**сверено**). DNS rebinding на практике закрывают проверка
   `Host` и токен, но требование MUST спеки не выполнено.
2. **У `openhands acp` нет песочницы.** §7 утверждал, что агент «переключается в контейнер», а сеть
   глушится `SANDBOX_NETWORK_DISABLED`. На деле CLI исполняет команды на хосте без изоляции — задача
   [OpenHands-CLI#472](https://github.com/OpenHands/OpenHands-CLI/issues/472) (**сверено**).
   Переменной `SANDBOX_NETWORK_DISABLED` нет ни в тексте arXiv:2511.03690, ни в документации V1.
   Ошибка ушла в сид `agents.json` и в [acpAgentsSpec.md](../manuals/acpAgentsSpec.md).
3. **Code lens и range formatting — не выигрыш переезда на `platform/lsp`.** §4 записал их в пользу
   платформенного клиента, но в нашем `lsp4ij-0.20.1.jar` уже есть `CodeLensCapabilityRegistry` и
   `DocumentRangeFormattingCapabilityRegistry` (**сверено** `unzip -l`).

Сверх этого неточно сформулировано условие пересмотра решения №73 (тема 1) и приведён неверный пример
в `functional.md:86` (тема 2).

## 1. LSP Client API в 2026.2 и решение №73

**Находки**

1. **Блог JetBrains** [первоисточник]: API клиента открыт для продуктов на открытой кодовой базе, работа
   начата в 2026.1.4. Переименования: `LspServer` → `LspClient`, провайдер → `LspIntegrationProvider`.
   Про DAP в посте ни слова —
   [blog.jetbrains.com](https://blog.jetbrains.com/platform/2026/06/open-sourcing-the-lsp-client-api-in-intellij-idea-2026-2/).
2. **Список ломающих изменений** [первоисточник]: по LSP там одна запись — в 2026.1
   (`LspServerManager` → `LspClientManager`). В 2026.2 и 2026.3 записей по LSP нет —
   [api-changes-list-2026](https://plugins.jetbrains.com/docs/intellij/api-changes-list-2026.html).
3. **DAP в платформе есть, но в закрытой части** [первоисточник]. Задача
   [IJPL-83441](https://youtrack.jetbrains.com/issue/IJPL-83441) «Debug adapter protocol support» решена
   21.06.2024 и доступна с 2024.2 (**сверено**). В открытом дереве `DebugAdapterSupportProvider` нет:
   `git grep` пуст (**сверено**).
4. **В платформенном клиенте нет файловых операций LSP**: греп по `platform/lsp/src` на
   `fileOperations`, `willRenameFiles`, `didRenameFiles` пуст (**сверено**). У LSP4IJ для этого есть
   `FileOperationsManager`. vtsls объявляет `didRename`, поэтому при переезде, скорее всего, пропадёт
   правка импортов при переносе файла — живьём не прогонялось.
5. **LSP4IJ 0.20.2 и 0.21.0 вышли 31.08.2026** (**сверено** через API
   [GitHub releases](https://github.com/redhat-developer/lsp4ij/releases)). В 0.20.2 — исправления
   фризов, ошибок потоков и утечек; у 0.21.0 заметок к выпуску нет. У нас закреплена 0.20.1
   (`vibe-plugins/deps/pins.env:12`).

**→ VibeIDEA**

Решение №73 остаётся в силе. Сам переезд — фича без патча платформы (EP открыт и `dynamic`), но польза
сегодня низкая: LSP4IJ всё равно остаётся ради DAP.

- **Уточнить условие (а) решения №73** — «DAP-модуль открыт в intellij-community»; сторож —
  `git grep -l DebugAdapterSupportProvider`. **Доки (тривиально)**, польза средняя.
- **Переписать цену переезда** в [platformLspVsLsp4ij.md](../knowledge/languages/platformLspVsLsp4ij.md):
  добавить потерю файловых операций, убрать мнимый выигрыш code lens и range formatting. **Доки**,
  польза средняя.
- **Поднять LSP4IJ до 0.20.2.** Версия живёт в трёх местах:
  - `vibe-plugins/deps/pins.env` — версия и sha256;
  - файл `vibe-plugins/deps/lsp4ij-<версия>.zip.sha256`;
  - `LibraryLicense` в `build/src/org/jetbrains/intellij/build/VibeIdeaProperties.kt:55`.

  Затем прогнать `checkVibeDist.sh`. **Конфиг**, польза средняя. На 0.21.0 — когда появятся заметки к
  выпуску.

## 2. ACP Registry и манифест agent.json

**Находки**

1. **Манифест агента** [первоисточник]: ни методов входа, ни возможностей в нём нет. Обязательны `id`,
   `name`, `version`, `description`, `distribution`. sha256 у binary-сборки необязателен — в правилах
   вклада это SHOULD ([agent.schema.json, CONTRIBUTING](https://github.com/agentclientprotocol/registry)).
   Блог [Zed](https://zed.dev/blog/acp-registry) — анонс без формата,
   [RFD](https://agentclientprotocol.com/rfds/acp-agent-registry) называет только адрес `registry.json`.
2. **Живой `registry.json`** (**сверено 11.09**):
   - 40 агентов, у 19 есть binary-дистрибуция (100 сборок), sha256 — у 53 сборок;
   - у девяти binary-агентов суммы нет вовсе: antigravity-acp, cortex-code, corust-agent, crow-cli,
     **cursor**, devin, junie, stakpak, vtcode;
   - OpenHands в реестре нет;
   - верхний уровень — `agents`, `extensions`, `version`.
3. **Вход по ACP** [первоисточник: [спека ACP](https://agentclientprotocol.com/protocol/v1/authentication),
   `.protocol-matrix/latest.md` в репозитории реестра].
   - `authenticate` вызывается только для методов, которые ведёт сам протокол.
   - Terminal Auth стабилизирован 20.08.2026: клиент объявляет `clientCapabilities.auth.terminal`,
     после входа переподключается и заново делает `initialize`.
   - Матрица протокола реестра (10.09): 20 из 33 агентов отвечают `auth_required` на `session/new`,
     12 умеют входить только через терминал.
4. **Карантин** [первоисточник]: `quarantine.json` лежит в репозитории реестра (8 агентов), но на CDN
   его нет (404), а сами агенты остаются в `registry.json`. Клиент, читающий CDN, карантина не видит.
5. **С 10.09** появились preview-канал и отдельные индексы под JetBrains; в них `claude-acp` помечен
   `bundled` и запускается с `--hide-claude-auth` [первоисточник].

**Сверка с репозиторием**

- **Дефект: доктор и Config Guard проверяют мёртвый файл** (**сверено**). Строка `doctor.line.acp`
  смотрит `.vibe/acp.json` (`VibeDoctorAction.kt:99, 231`), тот же путь стоит в `ConfigGuard.kt:64`.
  Агентов же читают из `.vibe/agents.json` и `~/.jetbrains/acp.json` (`AcpConfig.kt:57, 60`). Путь
  сменился 09.09, строки доктора остались прежними.
- **Входа по ACP у нас нет вовсе**: ни `authMethods`, ни `authenticate`, ни `auth_required` — греп
  пуст (**сверено**); в `clientCapabilities` нет `auth`.
- **«Уже добавлен» проверяется по имени** (`AgentRegistry.kt:147–151`). В реестре адаптер зовётся
  «Claude Agent», у нас — «Claude Code», и каталог предлагает его повторно (вывод по коду и живым данным).
- **Экрана выбора нет**: только `showInfoMessage` (`VibeAgentRegistryAction.kt:59–63`). `args` и `env`
  binary-сборки не читаются (`AgentRegistry.kt:121–131`).
- **`functional.md:86`** обещает sha256 «про каждую сборку» и приводит Cursor в пример, но у Cursor
  суммы нет.

**→ VibeIDEA**

- **Доктор и Config Guard — на `.vibe/agents.json` и машинный файл.** **Фича (малая, по сути баг)**,
  польза высокая.
- **Вход по ACP**: `authMethods`, `authenticate` для методов типа `agent`, Terminal Auth с
  переподключением, `logout` по объявленной возможности. **Фича (средняя)**, польза высокая: без него
  20 из 33 агентов реестра не открывают сессию, пока человек не войдёт в их программу руками. Метод
  подписки Claude — после решения по теме 3.
- **Экран выбора**: описание, репозиторий, иконка. Для binary без суммы — прямо «проверить нечем»,
  а не «—». «Уже добавлен» — по имени пакета без версии. **Фича (средняя)**, польза средняя.
- **Исправить `functional.md:86`.** **Доки (тривиально)**.
- **Вшивать снимок каталога сеялкой — не делать**: версии в реестре пинуются по нескольку раз в сутки,
  и снимок устареет в день сборки. Для офлайна хватит кэша последнего ответа по ETag. **Фича (малая)**,
  польза низкая.

## 3. Claude Code как ACP-агент на подписке Claude

**Находки**

1. [Статья поддержки 15036540](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)
   [первоисточник]: блок от 15 июня объявляет изменения приостановленными. Agent SDK, `claude -p` и
   сторонние приложения по-прежнему расходуют лимиты подписки, о переменах предупредят заранее, прежний
   текст оставлен для справки. 15.06.2026 — одновременно планировавшийся старт изменений и день
   объявления паузы. Более поздних обновлений нет. Пересказ в поиске про «новый запрет в
   августе–сентябре» — **слухи**.
2. [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) (**сверено**) — второй
   первоисточник к решению №65:
   - сторонним разработчикам нельзя предлагать вход Claude.ai в своих приложениях и гонять запросы
     через подписки пользователей;
   - нельзя собирать, хранить и пропускать через себя учётные данные — вход завершается только
     собственным потоком Anthropic;
   - конечному пользователю войти своей подпиской в немодифицированный Claude Code можно;
   - продукту, который запускает Claude Code, нельзя модифицировать бинарь, отключать или ограничивать
     встроенные методы входа.
3. **`claude auth status`** (**сверено**,
   [cli-reference](https://code.claude.com/docs/en/cli-reference)): выводит JSON (или текст с
   `--text`), код выхода 0 — вход есть, 1 — нет.
4. **Порядок источников оплаты** [первоисточник,
   [authentication](https://code.claude.com/docs/en/authentication)]:
   `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY` → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` →
   `apiKeyHelper` → `CLAUDE_CODE_OAUTH_TOKEN` → подписка.
5. **Адаптер [claude-agent-acp](https://github.com/agentclientprotocol/claude-agent-acp)**
   [первоисточник, исходники]:
   - методы входа — только терминальные и только если клиент объявил `auth.terminal`; их два — подписка
     и Console;
   - `--hide-claude-auth` прячет подписку;
   - адаптер сам шлёт `_auth/status_update` с меткой плана — это расширение через `_meta`, стандартный
     `auth/status` пока в статусе Draft.

**Сверка с репозиторием**

- Решение №65 подтверждено вторым первоисточником. Сид предлагает человеку войти самому, программой
  Anthropic, — это разрешённый путь.
- `AgentReadiness` ловит только `ANTHROPIC_API_KEY` (`AgentReadiness.kt:38, 57`, **сверено**).
  `ANTHROPIC_AUTH_TOKEN` и `CLAUDE_CODE_USE_*` тоже уводят с подписки, но не замечаются.
- Сид советует `"ANTHROPIC_API_KEY": ""`, а `AcpClient` кладёт в окружение пустую строку, не снимая
  переменную. Считает ли Claude Code пустое значение отсутствием, не документировано; **не проверено**.

**→ VibeIDEA**

- **«Чем платим»**: дополнить проверку `ANTHROPIC_AUTH_TOKEN` и `CLAUDE_CODE_USE_*`, а если агент
  прислал метку `_auth/status_update`, показывать её. **Фича (малая)**, польза высокая.
- **Строка доктора «вход Claude»**: `claude auth status`, смотреть **только код выхода** (в выводе есть
  e-mail и организация), с тайм-аутом; если `claude` нет на PATH — «не проверено». Учётных данных не
  касается, с №65 не спорит. **Фича (малая)**, польза средняя.
- **Запись в сиде — «Claude Agent»**, как в реестре. **Сид (тривиально)**, общий с VibeIDE, польза
  средняя.
- **Пустой ключ**: проверить одной командой; если пустая строка считается ключом, снимать переменную.
  **Фича (тривиальная)**, польза средняя.
- **Нужно решение владельца: кнопка входа через Terminal Auth для Claude.**
  - Рекомендация — показывать методы входа ровно так, как их объявляет агент, ничего не добавляя и не
    пряча. Вход ведёт программа Anthropic, учётных данных мы не касаемся, а ограничивать встроенные
    методы входа запрещает та же страница Legal.
  - Альтернативы: скрыть подписочный метод или включить `--hide-claude-auth`; во втором случае
    подписка отрезается целиком.
- **Не делать**: хранить `CLAUDE_CODE_OAUTH_TOKEN`, читать `~/.claude/.credentials.json` или
  Keychain, писать свой OAuth — всё это прямо запрещено.

## 6. MCP 2026-07-28: что наш сервер нарушает

**Находки** (все — первоисточник, **сверено** по страницам спеки)

1. **`server/discover`** отдаёт список версий в поле **`supportedVersions`** —
   [server/discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).
2. **Транспорт** ([streamable-http](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)):
   - `Origin` проверять обязательно (MUST), при неверном значении — 403;
   - `MCP-Protocol-Version` обязателен на каждом POST и должен совпадать с `_meta`, иначе 400 и `-32020`;
   - неподдерживаемая версия — **400** и `UnsupportedProtocolVersionError`;
   - неизвестный метод — **404** и `-32601`;
   - нет обязательного заголовка (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`) — проверка
     провалена;
   - значение `Mcp-Name` в форме `=?base64?…?=` сервер обязан декодировать перед сверкой.
3. **Схема**: у `-32022` поле `data` **обязательно** — `supported` (массив) и `requested` —
   [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema).
4. **Ревизия 2025-06-18**: на `initialize` с неподдерживаемой версией сервер **обязан ответить другой
   своей версией**, а не ошибкой; на `ping` обязан отдать пустой результат —
   [lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle),
   [ping](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/ping).
5. **[stacktr.ee](https://stacktr.ee/blog/mcp-2026-spec-changes)** — пересказ changelog, нового нет
   [вторичный].

**Сверка с репозиторием (сверено)**

- `McpServer.kt:91` отдаёт `protocolVersions` вместо `supportedVersions` — клиент по спеке списка
  версий не найдёт. Ошибка закреплена тестом `McpServerTest.kt:42`.
- Все ошибки JSON-RPC уходят с HTTP 200: у `Answer` статус по умолчанию 200 (`McpServer.kt:38`).
- У `-32022` нет `data` (`McpServer.kt:199–207`).
- `initialize` с чужой версией (например, `2025-11-25`) получает `-32022` (`McpServer.kt:76–81`)
  вместо встречного `2025-06-18`.
- `ping` получает «метод не поддерживается» (`McpServer.kt:146`).
- `MCP-Protocol-Version` не читается нигде; `Mcp-Method` необязателен (`McpServer.kt:62`), и
  [mcpSpec.md](../manuals/mcpSpec.md) (строка 36) это прямо обещает; base64 в `Mcp-Name` не
  декодируется.
- Заголовок `Origin` не читается — см. «Поправки».

**→ VibeIDEA**

- **Совместимость**: `supportedVersions`, `data.supported` / `requested`, встречная версия на
  `initialize`, `ping` → `{}`. **Фича (малая)**, польза высокая: клиент на `2025-11-25`, судя по коду,
  сегодня не договаривается о версии (живьём не проверено).
- **Статусы и заголовки**: HTTP 400/404 по спеке, строгие заголовки и `_meta` для запросов новой
  ревизии, base64 в `Mcp-Name`. **Фича (малая)**, польза средняя.
- **`Origin` → 403** при неверном значении. **Фича (тривиальная)**, польза средняя.
- **Самопроверка в докторе** по живому сокету: `server/discover` отвечает 200 и называет `2026-07-28`
  в `supportedVersions`, контрольный запрос с неверным `Mcp-Method` получает 400 и `-32020`; плюс
  наличие токена. **Фича (малая)**, польза средняя: юнит-тесты чистых функций проводку `VibeHttpApi`
  не видят.
- **`mcpSpec.md`** (строки 36, 66, 118) переписать под новое поведение. Новые русские литералы
  потребуют поправить числа в `i18nExclusions.txt`, иначе упадёт `checkVibeI18n.sh`.

**Не применимо**: OAuth (RFC 9728/9207, CIMD), `x-mcp-header`, SSE, `subscriptions/listen` — решения
№41 и №53.

     [GitHub changelog 02.06](https://github.blog/changelog/2026-06-02-cloud-and-local-sandboxes-for-github-copilot-now-in-public-preview/).

**Сверка с репозиторием**

- **Сид обещает изоляцию, которой нет**: в `agents.json:67–70` сказано «переключается в Docker» и дан
  совет `SANDBOX_NETWORK_DISABLED=true` (**сверено**). То же в
  [acpAgentsSpec.md](../manuals/acpAgentsSpec.md), в обеих копиях.
- **Шаги пайплайна идут без чекпоинтов** (**сверено**): снимок создаётся только в `sendToAcp`
  (`AgentPanel.kt:2660`), а `runPipeline` отправляет `c.prompt(...)` напрямую (`AgentPanel.kt:3652`).
  При этом `functional.md:157` обещает снимок «перед каждым сообщением агенту».
- `SECRET_USED` пишется только из команд проекта; запуск агента с `${secret:NAME}` в аудит не попадает.
- `ShellSafetyAnalyzer` судит каждую простую команду отдельно и не видит `curl … | sh`. Он портирован
  из VibeIDE дословно.

**→ VibeIDEA**

- **Запись OpenHands в сиде и спеке**: написать, что команды исполняются на хосте без песочницы, а
  изоляция есть только через Agent Canvas или SDK; `SANDBOX_*` убрать; статус CLI перепроверить к
  01.10.2026. **Сид (тривиально)** плюс доки, польза высокая: сейчас сид внушает защиту, которой нет.
- **Чекпоинт перед каждым шагом пайплайна**, роль — в метке. **Фича (малая)**, польза высокая: откат
  нужнее всего как раз в прогоне без присмотра.
- **Аудит границы**: при старте агента писать команду, `dir`, имена внедрённых секретов (`SECRET_USED`)
  и признак `terminal`, при выходе — код завершения. **Фича (малая)**, польза средняя.
- **Составное правило «сеть → pipe → интерпретатор»** в `ShellSafetyAnalyzer`, включая
  `sh -c "$(curl …)"`, синхронно с VibeIDE. **Фича (малая)**, польза средняя.
- **Контейнер для внешнего агента — не сейчас.** Понадобятся сопоставление путей `fs/*`, перевод
  `terminal/*` в `docker exec` и список разрешённых адресов вместо «сеть выключена», а готового
  Docker-слоя в community нет. **Фича (крупная)**, польза средняя.

## 11. (VibeIDE) Безопасность пакетов skills

**Находки**

1. **[arXiv:2604.02837](https://arxiv.org/abs/2604.02837)** (**сверено**) [первоисточник]: «Towards
   Secure Agent Skills: Architecture, Threat Taxonomy, and Security Analysis», Li, Wu, Ling, Cui, Luo,
   03.04.2026. Таксономия — 7 категорий, 17 сценариев, 3 слоя. Для нас главное:
   - разрыв согласия: одобряют одно, исполняется другое;
   - изменение скилла после установки;
   - вредный, отложенный и скачиваемый код в скриптах;
   - исходник скрипта в контекст модели не попадает, только его вывод;
   - одна из защит — доверие, привязанное к хэшу содержимого.
2. **[Infosecurity Magazine, 03.02.2026](https://www.infosecurity-magazine.com/news/malicious-crypto-trading-skills/)**
   [вторичный]: 386 вредоносных скиллов на ClawHub (в заголовке — «почти 400»). Механика — социальная
   инженерия: жертву уговаривают самой выполнить команду. Крадут ключи бирж и кошельков, SSH, пароли
   браузера. Цифры по кампании в разных источниках расходятся.
3. **[CrowdStrike Falcon Guardian, 01.09.2026](https://www.crowdstrike.com/en-us/press-releases/crowdstrike-unveils-falcon-guardian-ai-agent-security/)**
   [первоисточник]: цепочка из пяти звеньев — промпт, идентичность, вызов инструмента, использование
   скилла, системное действие — строится поверх endpoint-телеметрии. Разобран 09.09.
4. **Механизмы сообщества** [первоисточник]:
   - [спецификация Agent Skills](https://agentskills.io/specification): поле `allowed-tools` помечено
     Experimental; подписи, хэшей и песочницы в спеке нет;
   - [NVIDIA](https://docs.nvidia.com/skills/signing-agent-skills): подпись OpenSSF Model Signing поверх
     Sigstore **на весь каталог скилла**;
   - [OpenClaw](https://openclaw.ai/blog/virustotal-partnership): SHA-256 всего бандла плюс проверка
     VirusTotal.

   Три независимых источника считают единицей целостности **весь каталог скилла**.

**Сверка с репозиторием (сверено)**

- `SkillApproval.digest` — SHA-256 от шапки, тела и **отсортированных имён** вложений
  (`SkillApproval.kt:38–52`). Имена берутся с верхнего уровня, подкаталог становится одной строкой
  `scripts/` (`SkillsStore.kt:47–49`). **Ни содержимое вложений, ни имена внутри `scripts/` в digest не
  входят.**
- Пример на нашем же сиде: `resolve-merge-conflicts` велит запускать
  `python3 …/scripts/extract_conflict_context.py`. Pull request, переписавший этот скрипт, одобрения не
  отзывает: вердикт `UNCHANGED`, вопроса нет (`AgentPanel.kt:1899–1900`).
- Диалог одобрения показывает id и начало тела (`AgentPanel.kt:1901–1903`). KDoc в `SkillApproval.kt:31–33`
  и `SkillsStore.kt:20–21` утверждает, что он показывает `name` и `description`, — это не так.
- Скрипты исполняет внешний агент своим инструментом. В аудите не пишется, какой скилл и в какой
  версии участвовал в ходе.

**→ VibeIDEA**

- **Digest по всему каталогу скилла, рекурсивно**: отсортированные относительные пути плюс байты;
  `__pycache__` и `.DS_Store` исключать; лимиты глубины и размера — именованными константами. Туда же —
  рекурсивная проверка «ссылка наружу». **Фича (малая)**, польза высокая. После выпуска все одобрения
  один раз запросятся заново — сказать об этом в заметках к выпуску.
- **Диалог одобрения**: показывать `description`, объявленные `allowed-tools` и `compatibility`,
  список файлов с пометкой исполняемых; для изменённого скилла — какие файлы изменились (карта
  «путь → хэш» вместо одного digest). **Фича (малая)**, польза высокая.
- **Валидатор**: предупреждать на `curl … | sh`, `npx` и `uvx` без версии, зависимости PEP 723 без
  пина — и в теле, и в `scripts/`. **Фича (малая)**, польза средняя.
- **Аудит**: писать `skills: id@digest` в meta события `prompt`. **Фича (тривиальная)**, польза
  средняя. Формат журнала общий с VibeIDE — имя ключа согласовать.
- **`allowed-tools` — не предодобрение**: одной строкой в спеке скиллов. **Доки**, польза низкая.

**Не применимо**: песочница для скриптов — их исполняет внешний агент; подпись Sigstore — маркетплейса
нет, скиллы приходят сабмодулем через PR и перечислены в манифесте.

## 12. (VibeIDE) Общий контекст против изолированных субагентов

**Находки**

1. **[aiagentstore, 08.09.2026](https://aiagentstore.ai/ai-agent-news/daily/2026-09-08)** — **слухи,
   повтор снятого 09.09.** Страница снова говорит про роли, которые «координируются через общее
   контекстное окно», без единой ссылки. В [changelog GitHub](https://github.blog/changelog/label/copilot/)
   такого нет, а документация Copilot SDK описывает изоляцию.
2. **[Cognition, «Multi-Agents: What's Actually Working»](https://cognition.com/blog/multi-agents-working)**
   (22.04.2026) [первоисточник]: запись идёт в одном потоке, дополнительные агенты дают знание, а не
   действия. Ревью работает лучше, когда рецензент не видел контекста автора.
3. **[Anthropic, multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)**
   [первоисточник]: изоляция выигрывает на широком поиске (+90,2% ценой примерно 15× токенов) и
   проигрывает на коде, где мало по-настоящему параллельных задач. Результаты субагенты пишут в файлы,
   план ведущий хранит в памяти.
4. **Claude Code** [первоисточник]: по [документации субагентов](https://code.claude.com/docs/en/sub-agents)
   фазы, которые делят много контекста (планирование, реализация, тесты), лучше вести в основном
   разговоре; для последовательных задач [agent teams](https://code.claude.com/docs/en/agent-teams)
   советуют одну сессию или субагентов.
5. **[ACP](https://agentclientprotocol.com/protocol/session-setup)** [первоисточник]: у каждой сессии
   свой контекст, так что «свежий контекст» — это новая сессия того же агента.

**Сверка с репозиторием**

- **ACP-шаги пайплайна идут в сессию чата** (**сверено**). `runPipeline` берёт клиента через
  `ensureClient(agent)` (`AgentPanel.kt:3651`), а тот возвращает живой клиент с открытой сессией, если
  конфиг тот же (`AgentPanel.kt:3057–3063`). Значит, «резюме прошлого шага» дублирует то, что агент и
  так помнит, а `code-reviewer` судит, видя всю траекторию автора.
- Шаг на своей модели изолирован, но видит только пути и хвост ответа — то есть судит самоотчёт
  автора, а не код.
- План из `PlanStore` в промпт агента не попадает. Автопилот шлёт «продолжай по плану» без самого
  плана. Если сессию не удалось возобновить, новая сессия плана не знает.

**→ VibeIDEA**

- **Поле шага `context: "shared" | "fresh"`.** По умолчанию `fresh` для судящих ролей: новая
  `session/new` того же агента, её не запоминать, после шага вернуться в сессию чата. Для пишущих —
  `shared`. **Фича (средняя)**, польза высокая: ровно та схема, которую Cognition называет работающей,
  и параллелизм для неё не нужен.
- **Судье на своей модели — дифф затронутых путей** от чекпоинта шага, в пределах `maxTokens`; делается
  после чекпоинтов шагов из темы 10. Исключение из правила «не содержимое» записать решением в
  decisions. **Фича (малая)**, польза высокая.
- **Незаконченный план — в первый промпт новой сессии**, если прежнюю не удалось возобновить. **Фича
  (малая)**, польза высокая для автопилота.
- **Общее окно для параллельных ролей — не применимо**: шаги у нас последовательные, а источник
  недостоверен.
