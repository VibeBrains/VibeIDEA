# spotify/portal-ai-plugins: разбор и что взять (11.09.2026)

Разбор по просьбе владельца («вдруг есть что полезное взять в проект»). Репозиторий читался через
GitHub API, без клонирования и без запуска кода. Всё, что сказано ниже о VibeIDEA и VibeIDE,
проверено по их коду и спекам.

## Что это

Маркетплейс плагинов, который встраивает Spotify Portal — облачный Backstage от Spotify: каталог
сервисов, TechDocs, владение — в Claude Code, Codex и Cursor. Apache-2.0, 1238 звёзд на 11.09,
создан 23.07.2026, последний пуш — 17.08.2026.

- **Плагин `portal`** — шесть скиллов-инструкций (`setup`, `doctor`, `search`, `service`, `actions`,
  `feedback`) поверх `npx @spotify/portal-cli`. Манифесты трёх хостов (`.claude-plugin/`,
  `.codex-plugin/`, `.cursor-plugin/`) указывают на один каталог `skills/`.
- **Плагин `plugins/shunt`** (только Claude Code) — хуки `PreToolUse` на `Read` и `Bash`
  (`hooks/check-file-size`, `hooks/check-bash-read`) не дают дорогой модели читать большие файлы и
  отсылают к скиллам `bulk-reader` и `code-writer`, которые отдают работу дешёвому воркеру (AiKA,
  ассистент Portal) через тот же CLI. Рядом — `evals/`: табличные кейсы хуков и транспорта и три
  сквозных кейса.

Кода, который можно перенести, нет: всё завязано на Portal, AiKA и их CLI.

## Что взять

1. **Отказ хука в чужом формате — наша дыра, найденная на их ошибке.** `check-file-size` отвечает
   `{"decision": "allow"}` с кодом 0 — такого значения в схеме Claude Code нет (там
   `hookSpecificOutput.permissionDecision` — `allow`/`deny`/`ask`, а прежнее `decision` —
   `approve`/`block`); их эвалы сверяли хук с его же выводом, а не с контрактом хоста (issue #10).
   У нас обратная сторона того же: и `hooks/HookOutcome.kt` в VibeIDEA, и `common/hooks/hookOutcome.ts`
   в VibeIDE решают только по коду выхода, а stdout при коде 0 — заметка агенту. Хук, перенесённый
   из Claude Code, который отказывает JSON-ом с кодом 0, у нас **молча разрешает** — его «запрет»
   агент получает как совет. В обеих спеках хуков формат Claude Code не упомянут.
2. **Проверять, кто на самом деле ответил.** Неизвестное имя режима сервер Portal отвергает, а
   устаревший id — нет, поэтому `shunt` выбрасывает ответ, в котором нет имени применённого режима
   («the mode was not applied; the answer was discarded»). Наш аналог —
   модель: `LlmClient` пишет `model` в запрос и не читает её из ответа, а между нами и вендором бывают
   прокси, агрегаторы и цепочка запасных целей. Если ответила не та модель, за которую считается
   цена, сейчас этого не видно.
3. **Правила для навыков, которые меняют мир.** Скиллы `portal` держат дисциплину команд с побочными
   эффектами: `--help` у команды раньше, чем её флаги; `--json`, когда вывод читает агент; мутация —
   dry-run с `--json` → показать → явное согласие → выполнить, `--yes` — только для разрушительного
   действия и только с согласия, а успешный dry-run за выполнение не выдаётся; несколько инстансов —
   спросить, а не взять дефолтный; токены и коды авторизации в чате не просить и не печатать; текст
   с секретом не чистить молча, а просить переформулировать. В нашей спеке навыков из этого есть
   только пин версий `npx`/`uvx`, а их
   `npx @spotify/portal-cli` без версии — ровно то, о чём наш валидатор предупреждает в блоках кода.
   Место для правил — общий засеянный навык `update-skill` (он учит писать навыки) и спеки навыков
   обоих продуктов.
4. **В очередь — эвалы навыков.** `plugins/shunt/evals/evals.json` — формат skill-creator от Anthropic:
   `skill_name`, `description`, `evals[]` с `id`, `prompt`, `expected_output`, `files`,
   `expectations`. Раннера для этих кейсов в репозитории нет. В 17 засеянных навыках у нас нет ни
   одного эвала, а пайплайн с судьёй — готовый раннер.

## Что не берём и почему

- **`shunt` как механизм.** Наш `preToolUse` блокирует только в двух точках клиента — запрос
  разрешения и запись через `fs/write` (`hooksSpec.md`, «Граница ACP»); чтение агентом своим
  инструментом туда не входит. Экономия 82–94 % в README — это токены дорогой модели на
  Java-монорепо в 162 тысячи строк; расход воркера и проверка его результата в таблице не показаны.
  Это та ловушка, о которой предупреждает отчёт окупаемости `/cascade`.
- **Манифесты трёх хостов над одним `skills/`.** Мы хост, а не автор плагинов. Попутный урок из
  issue #11 — валидатор Claude Code резолвит источник-URL по сети и не читает локальный манифест:
  проверять каждый манифест по его пути, как это делает наш
  `VibeDefaultsTest.manifestMatchesEmbeddedResourcesExactly`.
- **MCP самого Portal.** Portal в нашей работе не участвует; понадобится — наш MCP-клиент ходит в
  его эндпоинт напрямую, плагин для этого не нужен.
- **Скилл `doctor`.** Диагностика у нас есть (`VibeDoctorAction`), и непроверяемое в ней уже не
  «здорово»: проба MCP без токена — `WARN`.
