# Каталог провайдеров `.vibe/providers/`: слоистость, семантика active, грабли

**Дата:** 2026-08-28 · **Ветка:** next · **Решение:** №24 в [decisions.md](../../decisions.md)

## Что построено

У VibeIDE `providers.json` дополнял **вшитых** провайдеров, а каталог `.vibe/providers/*.jsonc`
был библиотекой для копирования. У нас вшитых нет, поэтому каталог сделан **авточитаемым** —
он и есть «встроенные провайдеры», только обычными файлами. Реестр собирается из четырёх
слоёв, от слабого к сильному:

```
каталог ~/.vibe/providers/            (глобальные файлы, по алфавиту)
  → каталог <проект>/.vibe/providers/ (засеянный; по алфавиту)
    → ~/.vibe/providers.json          (пользовательский, глобальный)
      → <проект>/.vibe/providers.json (пользовательский, самый сильный)
        → resolveExtends (один строгий проход по слитому реестру)
          → фильтр active             (в самом конце)
```

## Главный урок: где лежат «встроенные»

Первая версия складывала слой «каталог + providers.json» на каждом уровне и мержила
уровни (проект сильнее глобали). Адверсариальное ревью поймало следствие: **засеянный в
каждый проект файл с `active:false` оказывался в самом сильном слое и глушил живой
глобальный `providers.json` пользователя с тем же id** (а активные сиды затирали его
baseURL/apiKeyEnv). У VibeIDE builtins лежат ПОД пользовательскими файлами — при переносе
«встроенных в файлы» их место в слоёнке обязано сохраниться: каталог — слабейший слой,
и только пользовательские providers.json дерутся между собой по правилу «проект сильнее».

## Семантика active: осознанно НЕ тристейт

Пробовали тристейт (`active: Boolean?`, патч без поля не переключает тумблер) — упало на
главном сценарии: пользовательский providers.json, писанный ДО появления каталога, без
полей `active`, наследовал `false` от одноимённого выключенного сида и умирал. Итог:
**запись без `active` считается активной**; патч, который не должен включать выключенную
запись, обязан явно повторить `"active": false` (строка в спеке). Обратная совместимость
пользовательского конфига важнее гиковского «патча без включения».
`models.fetch` при этом — честный тристейт (`ModelsFetch?`): «не задано» ≠ «true», иначе
`fetch: true` поверх базового `fetch: false` был бы невыразим.

## Прочие решения

- **Фильтр `active` — после слияния и resolveExtends**: `extends` работает от неактивной
  базы (клон при этом жив, если сам не скажет иного), активация — переопределением по id.
- **resolveExtends — один строгий проход по слитому реестру** (пофайловый lenient-проход
  был избыточен и давал два разных снимка базы); `overlay()` протаскивает `extendsId`
  (`over.extendsId ?: base.extendsId`), иначе патч терял отложенный extends. Extends
  одноуровневый, без цепочек.
- **Вшитых моделей нет** — `models.fetch` у активных (наш fetch ходит на `<baseURL>/models`,
  поэтому z.ai работает простым `true`). Static остаётся там, где каталог недоступен или
  врёт: Alibaba Coding Plan (каталог возвращает модели вне плана, имена сверяются
  посимвольно) и выключенные маршруты Meta Muse / minimax-anthropic (каталога нет).
- **Кастомные модели** (`models.static`) — фича «для гиков»: пример в
  `_template-openai-compatible.jsonc`, раздел в providersSpec.md; карандаш с путём файла в пикере
  и бейдж «кастом» на странице «Модели». Через кастомную модель включаются `vision:false`, `fim:true`,
  `extraBody`-квирки (thinking у Moonshot, tool_stream у DashScope/GLM).
- **Ключ без рестарта**: apply в «Провайдерах» публикует project-топик
  `ProvidersChangeListener.TOPIC` → открытая панель перечитывает реестр и каталоги моделей.
  Вотчер файлов на диске — отдельный пункт roadmap, топик покрывает только изменения из IDE.
- **Пустое поле ключа не удаляет запись хранилища, если ключа не было** — иначе две
  карточки с общим `apiKeyRef` (OpenCode Go/Zen: один аккаунт, один ключ) затирали друг
  друга в одном apply: близнец с пустым полем удалял только что сохранённое.
- **`listModels` = тот же транспортный контракт, что чат**: статические `headers`/`query`,
  query-auth в URL, `anthropic-version` для anthropic-протокола — иначе каталог Anthropic
  отвергал запрос, а query-auth провайдеры ходили за каталогом без ключа.

## Грабли

- **Kotlin: вложенные блочные комментарии.** `providers/*.jsonc` в KDoc — это `/*` внутри
  `/** … */`: вложенный комментарий съедает закрывающую `*/`, компилятор падает «Unclosed
  comment» в конце файла. Глоб-паттерны со `/*` в блочных комментариях писать нельзя.
- **Хвостовая лямбда против новых параметров с дефолтом.** Новый опциональный параметр
  ПОСЛЕ `onWarning: (String) -> Unit` ломает все вызовы `parse(text) { … }`: trailing
  lambda биндится к последнему параметру. Добавлять только ПЕРЕД лямбдой.
- **Откуда выкапывать «встроенных» VibeIDE** (для будущих переносов): baseURL —
  `electron-main/llmMessage/sendLLMMessage.impl.ts` и `aiSdkAdapter.ts` (OpenCode Zen
  `https://opencode.ai/zen/v1`, Go `https://opencode.ai/zen/go/v1`, OpenRouter
  `https://openrouter.ai/api/v1`); env-конвенции ключей — `common/vibeideSettingsTypes.ts`
  (`apiKeyEnvVarOfProvider`; у OpenCode env-имени осознанно нет — у нас введено своё
  `OPENCODE_API_KEY` + общий `apiKeyRef: "opencode"` на Zen и Go).
- **Сеялка не подчищает удалённое из манифеста:** снятый с засева providers.example.jsonc
  остаётся в уже засеянных проектах до release-обновления сидов (открытый пункт roadmap).

## Поля карточки `params` и `auth: "google-adc"` (29.10.2026)

Общий формат получил два расширения из хендоффа VibeIDE. У Groq, Mistral и Pollinations
ничего нового нет (обычные OpenAI-совместимые), а Vertex, Azure OpenAI и Bedrock требуют
адрес и заголовки, собранные из данных аккаунта; у Google Vertex ещё и токен, который
нельзя положить ни в `.env`, ни в связку ключей.

### `params`: значения, которые вводит человек

Провайдер объявляет список полей — массивом (`[{"name": "project"}, …]`) или объектом,
где ключ и есть имя. У поля есть `name`, необязательные `label`, `description`, `default`,
`optional` и `as`. Значение вводится в карточке провайдера и НЕ пишется в файл набора:
файл коммитится и раздаётся, а значения живут в `PropertiesComponent` под ключом
`vibe.providers.params.<id>.<name>` (не в связке ключей: это не секреты, а имя проекта,
регион, адрес ресурса).

Подстановка идёт в четырёх местах: `baseURL`, строковый `models.fetch`, значения `headers`
и `query`. Плейсхолдер — `{name}`. Введённое значение сильнее объявленного `default`.
Смысл полей:

- обязательное без значения — провайдер остаётся в каталоге и на странице «Провайдеры»,
  но `ProvidersService.resolve` возвращает null с предупреждением, и запросов нет;
  это важнее, чем «удалить провайдера»: человек должен видеть, чего не хватает;
- `optional: true` без значения — пустая подстановка; если на пустом плейсхолдере
  держалось ВСЁ значение заголовка или query-параметра, он выпадает целиком, а не уходит
  пустой строкой;
- `{x}` посреди текста (`"Bearer {token}"`) при пустом `x` оставляет `"Bearer "` — заголовок
  значим и без значения, поэтому не выпадает;
- `as: "headers"` — значение разбирается как JSON-объект и вливается в `headers`;
  невалидный JSON или не объект не добавляет ничего и не роняет провайдера — тихая дыра,
  которую стоит закрыть предупреждением, если поле начнут использовать шире;
- неизвестный плейсхолдер остаётся как написан: опечатка видна в запросе, а не превращается
  в пустоту.

Слияние слоёв: `params` — обычное необязательное поле, пустой список у сильного слоя
не стирает поля нижнего (`over.params.ifEmpty { base.params }`). `extends` наследует поля
так же, как остальные свойства. Каталог моделей должен ходить на УЖЕ раскрытый `models.fetch`
(`resolved.entry.modelsFetch.url`), иначе поле в строке URL молча не сработает.

### `auth: "google-adc"`: токен из Application Default Credentials

Ключа нет, есть файл учётных данных, который Google кладёт сама: путь из
`GOOGLE_APPLICATION_CREDENTIALS`, иначе `~/.config/gcloud/application_default_credentials.json`
(на Windows — `%APPDATA%\gcloud\...`). Поддержаны оба вида, которые выдают `gcloud auth
application-default login` и сервисный аккаунт:

- `authorized_user` — refresh-токен меняется на access-токен запросом к `token_uri`
  (`grant_type=refresh_token`);
- `service_account` — RS256-JWT с `aud`, `iat`, `exp` (+1 час) и
  `scope=https://www.googleapis.com/auth/cloud-platform`, подписанный закрытым ключом
  из `private_key` (PKCS#8), затем тот же обмен на токен (`grant_type=jwt-bearer`).

Токен кэшируется по пути файла и обновляется за минуту до `expires_in`; запрос всегда берёт
актуальный. Ошибка чтения, подписи или обмена — предупреждение с причиной и остановка
провайдера, а не запрос с пустым `Bearer`. В запрос уходит `Authorization: Bearer <токен>`;
ключ при этом не ищется ни в связке, ни в `.env` (`ApiKeyResolver` для этого типа сразу
возвращает null). Поэтому `google-adc`-провайдер не попадает в общий список «нет ключа»
и не показывает поле ключа в карточке — вместо него кнопка «Проверить».

Реализация — только JDK (`java.net.http.HttpClient`, `Signature`): новая зависимость
Google SDK не нужна, а обмен и подпись проверяются юнит-тестами без сети.

### Где это в коде и что проверено

- `ProvidersFile.kt` — разбор `params` (массив и объект), `AuthSpec.GOOGLE_ADC`
- `ProviderParams.kt` — чистая `prepare`/`substitute` и хранилище значений
- `GoogleAdc.kt` — путь, разбор, подпись, обмен и кэш токена
- `ProvidersService.resolve` — сначала `prepare`, потом ключ; `null` = запросов нет
- `VibeProvidersConfigurable.kt` — поля карточки, сохранение и проверка
- `AgentPanel.kt`, `VibeModelsConfigurable.kt` — каталог моделей ходит на раскрытый адрес

Тесты: `ProviderParamsTest` (оба написания, обязательное/необязательное, `as: headers`,
слияние, ключ настроек), `GoogleAdcTest` (тело обмена, JWT и подпись, запас свежести,
путь на Unix/Windows, размещение заголовка). Гейты i18n/imports/comments пройдены.

Не проверено: живая IDE и настоящий аккаунт Google (в worktree нет ни того, ни другого).
Точная форма `params` в новых файлах набора не сверена: submodule `vibeDefaults` в этом
окружении пуст, поэтому разбор принимает обе формы, а гейт ключей сидов считает `params`
свободным объектом.
