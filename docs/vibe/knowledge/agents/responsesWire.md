# Провод Responses: вендор проверяет пары элементов, и ломается всё на повторе

**Дата:** 23.09.2026 · **Повод:** пункт 16 бэклога разбора дайджеста 23.09 — GPT-6 с инструментами

## Суть

`/v1/responses` — не диалект chat/completions, а другой эндпоинт с другой моделью разговора.
Разговор там — список элементов: сообщения, рассуждение, вызовы функций, их результаты.
Сам запрос собрать просто.
Трудное — вернуть модели её прошлый ответ так, чтобы вендор его принял:
он проверяет, что элементы стоят парами, и отвергает запрос с 400 при разрыве любой пары.

Что проверяется, по сообщениям об ошибках вендора и по его же клиенту (openai/codex):
- **вызов без результата** — «No tool output found for function call»
- **рассуждение без следующего за ним элемента** — «reasoning was provided without its required following item»
- **вызов с id элемента, но без рассуждения, из которого он вышел** — «function_call was provided without its required reasoning item»

## Как устроено у нас

- **Без хранения у вендора** (`store: false`).
  О разговоре у вендора не лежит ничего, а рассуждение едет зашифрованным содержимым элементов:
  в этом режиме вендор отдаёт его по умолчанию (developers.openai.com/api/docs/guides/reasoning).
  `include: ["reasoning.encrypted_content"]` не шлём: по документации в этом режиме содержимое приходит и без него (Codex его шлёт всегда).
- **Выход модели возвращается дословно.**
  Рассуждение, слова и вызовы раунда хранятся с раундом и с финальным ответом (`ResponsesReplay`) и уходят обратно в том же порядке.
  Берутся только из `response.output_item.done`: в `output_item.added` зашифрованное содержимое может быть неполным (openai-python, `ResponseReasoningItem`).
  От элемента остаются поля, которые принимает вход и которые шлёт обратно Codex, включая `phase` у сообщений — вендор просит её не терять.
- **Только той же модели того же провайдера.**
  Зашифрованное рассуждение — состояние этой модели, и ничто не документирует, что его примет другая.
  Другая модель получает текст и вызовы **без id элементов**: id привязывает вызов к рассуждению, которого в запросе нет.
- **Разрыв пар лечится до отправки, а не после 400** (`ResponsesAccumulator.items`):
  - ответ, оборванный на рассуждении, теряет хвостовое рассуждение
  - рассуждение без зашифрованного содержимого не отправляется вовсе, а остальные элементы ответа уходят без id
  - сообщение с одним лишь отказом (`refusal`) остаётся: без него рассуждение перед ним осталось бы без пары
  - ход, закончившийся на вызовах без результатов (стоп, потолок раундов), выход модели не сохраняет

## Грабли рядом

- **Отказ здесь — не причина остановки.**
  Ответ завершается как обычно, а на месте текста стоит часть `refusal`.
  Непрочитанная, она давала пустой ответ, выглядящий законченным; теперь это `StopReason.REFUSAL` с текстом вендора.
- **Краткое изложение рассуждения не запрашиваем.**
  Вендор пишет, что для него может понадобиться верифицированная организация, и отказ получил бы весь запрос, а не одно изложение.
  Поток его всё равно читается: сервер, который шлёт рассуждение без просьбы, его покажет.
- **Запись в кэш на chat/completions не читалась.**
  `prompt_tokens_details.cache_write_tokens` входит в `prompt_tokens`, и до 23.09 запись считалась по цене обычного входа.
  У GPT-6 запись дороже входа на четверть, а цена записи в сиде была объявлена — и не применялась.
- **Копия и ветка треда теряли раунды инструментов.**
  `HistoryStore.duplicate` и `branch` пересобирали запись поимённо и не знали о полях, появившихся позже.
  Нашлось, когда к записи добавилось ещё одно поле.
- **Sol и Luna на chat/completions** принимают инструменты только при `reasoning_effort: "none"`.
  Там ход с инструментами уходит без рассуждения, и лента один раз говорит почему (`TOOLS_NEED_NO_REASONING`).
  Astra на chat/completions функций не вызывает вовсе (`TOOLS_ONLY_ON_RESPONSES`).
