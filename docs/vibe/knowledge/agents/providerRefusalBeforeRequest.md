# Отказ провайдера, названный до запроса: дубли инструментов и вывод fast mode

**[решение + грабли]**

## Контекст

Два отказа вендора за разбор 30.10–09.11.2026 стоили бы целого хода, а ловятся на нашей стороне до отправки.

Первый — дублирующееся имя инструмента. У двух MCP-серверов может быть инструмент с одним именем, а обновлённый
`tools/list` может приехать рядом со старым определением. Провайдер получает два `tool` с одинаковым `name` и отвергает
весь запрос (`duplicate tool declaration`, Kimi Code 2.5.2). Модель называет инструмент по имени, поэтому второе
определение не добавляет ничего: это тот же вызов.

Второй — `speed: "fast"` у Claude Opus 4.8. С 30.11.2026 вендор отвечает на него ошибкой, тогда как у Opus 5.5 fast mode
остаётся. Сам клиент поле не шлёт ни на одном проводе; единственный путь — рукописный `extraBody` в файле провайдера.

## Решение

- `providers/ToolCalls.distinct` — одно определение на имя, первое по порядку. Функция стоит в `openAiTools`,
  `anthropicTools`, `geminiTools` и `ResponsesWire.tools`: провод не выбирает это поведение заново, а получает уже
  очищенный список. Первое определение сохраняется, порядок не меняется, поэтому кэш префикса страдает меньше всего.
- `ExtraBodyConflicts.Reason.FAST_MODE` — конфликт для `^claude-opus-4-8` на Anthropic-проводе. Доктор показывает строку
  `doctor.extraBody.fastMode` рядом с остальными находками `extraBody`; `claude-opus-5-5` не задет.
- Тесты: `ToolCallsTest` (дубль на всех четырёх проводах) и `ExtraBodyConflictsTest` (4.8 против 5.5 и чужой провод).

## Границы

Дедупликация выбирает первое определение, а не самое свежее: если сервер поменял схему инструмента, а рядом осталось
старое определение с тем же именем, уйдёт старое. Для обновлённой схемы сервер должен перестать отдавать прежнюю запись —
иначе мы не знаем, какая из двух верна, а молча взять последнюю значило бы менять поведение по порядку ответа.
