# Чекпоинт хода: ссылка держит снимок, контракт общий с VibeIDE

[gitAndTools] · 16.10.2026 · переход на общий контракт набора

## Контекст

Чекпоинты VibeIDEA и VibeIDE работают в одном репозитории, но снимки были у каждого свои:
здесь коммит с родителем HEAD и подписью пользователя, без ссылки, откат через `git restore` без удаления.
Контракт один для обоих: `checkpointSpec.md` и `testVectors/checkpoint.json` общего набора `.vibe`
(подмодуль `vibeDefaults`). Чистая часть — `checkpoints/CheckpointContract.kt`, git — `CheckpointService.kt`.

## Суть

- **Без ссылки снимок недостижим, и `git gc --prune=now` его удаляет.** Проверено на git 2.54: `commit-tree` без `update-ref`,
  после `gc --prune=now` `cat-file -e` отвечает «нет такого объекта». Прежние чекпоинты жили до первой сборки мусора.
  Теперь на коммит ставится `refs/vibe/checkpoints/<sha>`; `CheckpointServiceTest` гоняет `gc --prune=now` и проверяет, что объект жив.
- **Пространство `refs/vibe/` не видно в `git branch` и не уходит обычным `git push`.** Снимки пайплайнов (`refs/vibe/pipelines/…`) уборка не трогает.
- **Подпись — через `GIT_AUTHOR_*` / `GIT_COMMITTER_*` продукта.** `commit-tree` без личности падает, а у репозитория её может не быть;
  `user.name` пользователя на историю снимков не попадает. Тест ставит в репозитории пустые `user.name` / `user.email` — снимок всё равно создаётся.
- **Родителя у снимка нет.** Снимок не примыкает к ветке пользователя и не тянет её историю.
- **Откат — план, подтверждение, запись.** Список файлов снимка — `ls-tree -r -z`, папки — `ls-files -z --cached --others --exclude-standard`
  (игнорируемые в него уже не входят). Без `-z` git берёт в кавычки имена с не-ASCII знаками, и такие файлы на диске не находятся.
  Запись — `read-tree` + `checkout-index -a -f` во временном индексе (копия настоящего), потом удаление файлов плана.
  Настоящий индекс и HEAD после отката байт в байт те же — это проверяет тест. В число удаляемых не входят пути, которых уже нет на диске, и каталоги (подмодули).
- **Лента и коммит разделены.** `.vibe/local/checkpoints.jsonl` хранит метку, время и тред для ленты; ход, ничего не изменивший в папке,
  не делает нового коммита, но попадает в ленту с той же ссылкой — без записи в ленте откат к сообщению не нашёл бы снимок своего хода.
- **Живое множество для уборки — последние 500 записей ленты** (`MAX_JOURNAL_ENTRIES`). Лента сама ничего не удаляла, и без предела
  уборка не снимала бы ничего никогда. Предел — константа, не настройка: решение продукта, а не пользователя. Ссылка моложе часа щадится при любой ленте.
- **Старые записи ленты** (до ссылок) при чтении: коммит ещё есть — ставится ссылка; нет — запись помечается недоступной, откат к ней не предлагается.

## Какие вызовы ACP-агента считаются командами

Контракт считает команды по именам прямого чата (`run_command`, `run_persistent_command`, `run_nl_command`), сравнивая точно.
У ACP-агентов имена свои (`Bash` у Claude Code, `run_shell_command` у Gemini CLI и так далее). Решение: строка вызова записывается в тред
под именем `run_command`, если у вызова вид `execute` (ACP-спецификация: «запуск команд»), либо имя уже известно аудиту как командное (`ToolCallAudit`).
`BashOutput` и `KillShell` команд не запускают и остаются под своими именами. Имена агентов, кроме `Bash`, взяты из аудита и из памяти о чужих агентах, прогоном не подтверждены;
вид `execute` — главный признак, имя — запасной. Вид может прийти в `tool_call_update`, а не в объявлении: такая строка останется под своим именем, и команда не будет сосчитана.
У строк, записанных до этого изменения, имени нет — предупреждения по ним не будет.

## Применение

- Новый случай формата, уборки или предупреждения — в `testVectors/checkpoint.json` общего набора, а не в тест одной стороны.
- Не складывать снимки вне `refs/vibe/checkpoints/` — там действует уборка.
- Продукт-сосед читает наш снимок разбором `parseMessage`; `CheckpointVectorsTest` проверяет и собственную запись обратным чтением.
