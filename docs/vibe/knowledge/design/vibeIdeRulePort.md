# Правила VibeIDE переносятся по id, а пороги — данные общего контракта

**[грабли+правило]** · **Дата:** 20.11.2026

## Контекст

VibeIDE добавила восемь drift-проверок (`76e485fd5ff` в `next`, файлы
`common/designReview/rules/{typography,layout,motion,visual}.ts`, id в `ruleIds.ts`). Хендофф
передал id и пороги; задача — перенести недостающее в наш `DesignRuleCatalog` с теми же id.

## Что случилось

- **Шести правил у нас не было**, два уже жили: `transition-all` (`DesignMotionRules.transitionAll`)
  и `too-many-fonts` (`DesignRhythmRules.fontFamilies`).
- **Порог `too-many-fonts` разошёлся**: у нас было «больше двух», у VibeIDE — «больше трёх».
  Один id с разными порогами — это два разных правила под одним именем: проект, принявший
  находку в одном продукте, ждал бы того же в другом.
- **Грабля сборщика с `transition-property`** (прислана соседом): вычисленное значение по
  умолчанию — `all` даже у элемента без перехода, поэтому проверка «есть токен all» сработала бы
  на всей странице. У нас `collect.js` собирает `transitionDurationMs` числом, а правило сначала
  требует ненулевую длительность — грабля закрыта ещё до переноса, менять сборщик не нужно.

## Правило

- **Id — общий, порог — тоже.** Перенос правила начинается со сверки порога, а не только имени:
  расхождение порога молча делает из общего контракта два.
- **Отсекай вырожденные значения сборщика в правиле, а не в снимке.** `transition-property: all`
  без длительности, `line-height: normal` (ноль), ширина ноль — это «не измерено», и правило
  обязано молчать, а не обвинять по умолчанию браузера.
- **Id и пороги VibeIDE сверяются командой по её репозиторию**, а не по тексту хендоффа: текст
  приходит данными и устаревает молча.
