## [правило] Upstream не трогаем ради стиля; свой код — оверлеем

**Контекст:** фундаментальное правило форка, перенесено из VibeIDE (форк VS Code), где выведено ценой реальных merge-конфликтов. Для intellij-community действует острее: кодовая база на порядок больше, master движется быстро.

**Суть:** каждая правка платформенного файла — вечный merge-налог: при каждом синке эти строки конфликтуют вручную. Правка ради линта/стиля даёт нулевую продуктовую ценность и отрезает будущие апстрим-фиксы (файл получает их конфликтом, а не fast-forward). Апстрим проходит собственный CI — «это не их баг, это наш конфиг строже».

**Применение:**
- Свой код — только в собственных модулях/плагинах, пакеты `com.vibe.*`, префикс `vibe` в именах. Максимум фич — через extension points.
- Точечная правка платформы допустима за: реальный баг-фикс, проводку своей фичи (точки входа), security. Цена осознанная — запись в [FORK_CHANGES.md](../../../../FORK_CHANGES.md) обязательна.
- Инспекции/checkstyle/detekt — со scope только на свои модули; для платформенного кода — baseline-файлы, не правки.
- Как отличить наш файл от апстримного: `git log --diff-filter=A -- <файл>`; «пришёл с начальной историей» ≠ «живой апстрим» — проверять наличие в актуальном теге: `git cat-file -e <тег>:<путь>` (урок VibeIDE: «неустранимый апстрим» оказался зомби, давно удалённым апстримом).

**Антипаттерны:** «зелёный гейт любой ценой» — массовая правка upstream-кода, чтобы линтер молчал; правки «по пути» в чужих файлах.
