# Сборка инсталлятора под Windows
← [Knowledge Index](../README.md)

**[грабли]** Проверено 02.09.2026 при сборке Windows-артефактов v0.3.0 на чистой машине (Windows 11,
50 ГБ ОЗУ, 16 потоков). Всё ниже — не «особенности Windows вообще», а то, на чём реально стояла
сборка, и как оно закрыто.

## Клон падает на полпути и оставляет пустой индекс

Самый длинный путь в репозитории — 234 символа; с префиксом каталога клона это больше 260, и без
`core.longpaths` git прерывает чекаут на первом таком файле. Симптом обманчив: `git status`
показывает **все** 281 797 файлов как staged-удалённые (`D `), а лежащие на диске — как untracked.
Это не удаление, это индекс, который git не успел заполнить (в reflog одна запись — `clone`).

Лечение без переклонирования:

```bash
git reset -q                      # индекс из HEAD; рабочее дерево не трогается
git config core.longpaths true
git restore --source=HEAD --worktree :/
```

После этого дерево чистое. Клонировать сразу правильно: `git clone -c core.longpaths=true …`.
Системный `LongPathsEnabled` тут ни при чём — git ходит по своему пути через `\\?\`.

## `python3` на Windows — заглушка магазина Microsoft

Команда есть на PATH, печатает «Python was not found; run without arguments to install…» и
выходит с ошибкой; настоящий интерпретатор зовётся `python`. Три гейта из четырёх на этом
падали. Решение — один резолвер `vibe-plugins/tools/pythonBin.sh`, который **запускает** кандидата
(`python3`, затем `python`), а не ищет его по имени, и кладёт результат в `$PYTHON`; все скрипты
инструментов его подключают.

Это возвращается с каждым новым скриптом и с каждым новым блоком в старом. Счёт на 04.09.2026: три
раза за сутки — выросший `checkVibeUi.sh` (проверка значков и токенов), затем `checkVibeReleaseNotes.sh`
вместе с его вызовом из `releasePublish.sh` (публикация упала бы на самом гейте заметок), затем ещё
два новых Python-блока в том же `checkVibeUi.sh`, дописанных на macOS уже после первой правки.
Признак один и тот же — гейт печатает текст про Microsoft Store вместо своего вердикта.

Правило: **пишете новый скрипт или новый Python-блок в старом — зовите `"$PYTHON"`**, а не `python3`
(резолвер подключается первой строкой после `cd`). Пока это держится на внимательности, оно будет
возвращаться: дешёвый guard — проверка «в `vibe-plugins/tools/*.sh` нет прямого `python3`» — не
заведён, решение за владельцем.

## Python на Windows пишет `\r\n` в конвейер

`print()` из python.exe под Git Bash отдаёт строки с `\r\n`, и всё, что bash читает из него —
`read`, `mapfile`, `$(...)` — уносит `\r` в сравнение: сухой прогон публикации сказал «sha256 не
совпадает со штампом» на файле, чей хеш совпадал побайтно. Срезать `\r` в каждом потребителе —
значит забыть в следующем; поэтому `pythonBin.sh` отдаёт в `$PYTHON` не бинарь, а обёртку
`pythonLf.sh` (`"$VIBE_PYTHON_BIN" "$@" | tr -d '\r'` с `pipefail`), и вызовы во всех скриптах
одинаковы на любой ОС.

## Разделители путей внутри гейтов

Индекс базы знаний и список исключений локализации написаны через `/`, а `os.walk` на Windows
отвечает через `\`. Без нормализации гейт документации считал все 21 запись «без строки в
индексе», а храповик локализации не находил ни одного исключения и насчитывал 91 «интерфейсный»
литерал при планке 0. В обоих местах сравнение идёт по `path.replace(os.sep, '/')`.

## `strings` нет — индекс плагинов читается grep-ом

Гейт дистрибутива считал упоминания LSP4IJ в двоичном `plugin-classpath.txt` через
`strings | grep -c`. В Git Bash нет binutils; `grep -a -o -i lsp4ij | wc -l` даёт то же самое
без внешней утилиты и работает на обеих ОС.

## Иконка и картинки инсталлятора — те же грабли, что Dock на macOS

`WindowsCustomizerBuilder` без `icoPath` берёт стоковый `build/idea-community-images/win/product.ico`
(иконка IntelliJ на панели задач и в ярлыке), без `installerImagesPath` — стоковые
`headerlogo.bmp`, `logo.bmp`, `install.ico`, `uninstall.ico` внутри NSIS-инсталлятора, а
унаследованный `uninstallFeedbackUrl` открывает опрос JetBrains об удалении IDEA. Всё четыре
поля заданы в `VibeIdeaProperties.createWindowsCustomizer`.

Файлы генерирует `vibe-plugins/tools/makeWinImages.py` из **того же** `vibeidea.icns`, что и
Dock-иконка (Pillow читает icns и пишет ico с BMP-кадрами, которые понимает генератор лаунчера):
`vibeidea.ico` 16–256 (16 и 32 — упрощённые кадры из icns, остальные — downscale 256),
`install.ico`/`uninstall.ico` 16–48, шапка 150×57 и боковая панель 164×314 на тёмном фоне бренда
с неоновыми пятнами. ImageMagick/Inkscape на машине не нужны; Pillow ставится в любой venv.

Что **не** трогали и почему: `baseFileName` унаследован от IDEA CE, поэтому лаунчер в архиве
зовётся `idea64.exe`, а рядом лежат `idea64.exe.vmoptions` и `idea.properties`. Переименование
задевает конфиг-каталоги и обе другие ОС — отдельное решение, не правка «по пути».

## `vibeidea-build.bat` не работал ни разу: LF-переводы строк убивают .bat

**[инцидент] 04.09.2026, первый живой прогон штатной точки входа.** `.gitattributes` апстрима
объявляет `* text=auto eol=lf`, то есть **все** файлы выкладываются с LF — включая наши батники. А
`cmd.exe` разбирает `.bat` построчно и на LF ломается так, что:

- `@echo off` не срабатывает, и каждая строка печатается как команда;
- `%~dp0` пустеет — скрипт ищет `\android\` и `\vibe-plugins\tools\checkVibeDist.ps1` от корня диска;
- строки `rem` с кириллицей исполняются как команды («`'не' is not recognized`»);
- и главное — **скрипт заканчивается кодом 0**. «Успех» без единого выполненного шага.

Лечение — правило в корневом `.gitattributes` (запись в [FORK_CHANGES.md](../../../../FORK_CHANGES.md)):

```
*.bat	text eol=crlf
```

`*.cmd` намеренно не трогаем: у апстрима это двойные bash+batch файлы, и CRLF сломал бы их
bash-половину на Unix. После правки атрибута рабочую копию надо перевыложить
(`rm файл && git checkout -- файл`) — сам по себе атрибут уже лежащий файл не переписывает.

Плюс `chcp 65001 >nul` в начале батника: файл в UTF-8, а консоль по умолчанию в OEM-кодировке, и
русские сообщения выходили мусором.

## `tar` в download.ps1 брался из PATH — и это GNU tar из Git for Windows

Скрипт звал просто `tar`, рассчитывая на системный bsdtar (`C:\Windows\system32\tar.exe`). Но у
всякого, кто клонировал репозиторий, стоит Git for Windows, и его `usr/bin/tar` (GNU) находится в
PATH раньше. GNU tar считает обратный слэш частью имени, а не разделителем, и падает на
`-C extracted\servers\dap\vibeJsDebug` с «Cannot open: No such file or directory» — про каталог,
созданный строкой выше. Из чистого PowerShell тот же скрипт работал, из Git Bash — нет.

Лечение: звать `$env:SystemRoot\system32\tar.exe` по полному пути и передавать каталог через «/».

**Общее правило обеих находок:** скрипт, написанный на одной ОС и «проверенный» чтением, на другой
ОС не проверен. Оба дефекта нашлись за десять минут первого настоящего запуска — и оба до этого
жили в репозитории как «готовые».

## Сабмодуль сидов после `git pull` остаётся на старом коммите

`git pull` обновляет указатель на `vibeDefaults`, но **не трогает рабочую копию** сабмодуля: она
остаётся там, где её оставила прошлая сессия. Собранный дистрибутив при этом валиден, гейт зелёный,
и потеря видна только тому, кто откроет `.vibe` в новом проекте: 04.09.2026 сборка 0.4.0 на Windows
чуть не уехала со старым набором — без образцов `.http`, окружений и подключений к БД, то есть без
половины того, что этот выпуск обещает.

Признак — `git status` показывает сабмодуль как изменённый, а `git diff --submodule=log` печатает
**`(rewind)`** и список коммитов, которых в рабочей копии нет. Лечение до сборки:

```bash
git submodule update --init vibe-plugins/vibe-agent/resources/vibeDefaults
```

Правило простое: `git pull` на сборочной машине всегда парой с `git submodule update --init`, и
`git status` перед сборкой читать до конца, а не до первой знакомой строки.

## Клон `android/` — по дате синка с апстримом, не по HEAD

Плейбук в FORK_CHANGES.md обновляет клон на `master` HEAD, потому что делается в момент синка.
Сборка **позже** синка должна брать android на дату базы платформы, иначе получаешь переименованные
таргеты (`no such target '@@lib+//:…'`). Быстрый способ без полной истории (репозиторий велик):

```bash
git clone --shallow-since=2026-08-28 https://github.com/JetBrains/android.git android
git -C android checkout "$(git -C android log --before='2026-08-31T18:17:08+03:00' -1 --format=%H origin/master)"
```

Дата — из коммита синка (`git log -1 --format=%ci <sync-commit>`).

## Phpactor на Windows: две разные проверки, и чинили сначала не ту

**[инцидент] 04.09.2026.** Заголовок релиза 0.4.0 обещал «PHP на Windows заработал». На живой
Windows-машине сервер не стартовал вовсе:

```
Phpactor requires the following PHP extension(s) which are not loaded: mbstring, posix.
```

Проверок в phar **две**, и они срабатывают в разном порядке:

| Чья | Где | Когда бьёт | Чем отключается |
|---|---|---|---|
| Box (сборщик phar) | стаб phar | после собственной проверки Phpactor | `$_SERVER['BOX_REQUIREMENT_CHECKER']=0` |
| Phpactor | `bin/phpactor`, первые строки | **всегда** на Windows | ничем: `extension_loaded('posix')` + `exit(255)` |

Чинили Box, а падает Phpactor: до Box дело просто не доходит. Обход из 0.4.0 (`-d
auto_prepend_file=…`, гасящий Box) не менял ничего.

**Почему проверка на macOS этого не увидела — главное здесь.** «Эмуляция Windows» отключала
*функции* `posix_*` через `disable_functions`. Но проверка смотрит не на функции, а на **расширение**,
и `extension_loaded('posix')` при отключённых функциях остаётся `true`. То есть эмулировалось
ровно не то условие, на котором Windows и падает: отсутствие расширения нельзя изобразить
отключением функций. Гейт был зелёным на macOS и на Windows не запускался ни разу — обещание уехало
в релиз.

**Решение** (0.4.0, сборка Windows): лаунчер `vibe-plugins/deps/phpactorLaunch.php` едет рядом с
phar, находит его по `__DIR__`, поднимает `phar://…/vendor/autoload.php` и отдаёт управление
`Phpactor\Application` — то же, что делает `bin/phpactor`, минус один `array_filter` с расширениями.
Проверка версии PHP сохранена: без неё «нужен PHP 8.2» превратилось бы в трассу из автозагрузчика.
Symfony читает `$_SERVER['argv']`, а не `$argv` — не переписав его, получаешь «no commands defined
in the "D" namespace» (имя команды берётся из пути `D:\…`).

Факты, снятые запуском на Windows 11 с PHP 8.4 **без `php.ini`**: `--version` печатает версию,
`initialize` отвечает с `completionProvider` и `definitionProvider`. `mbstring` в списке требований
есть, но серверу не нужен — без него ответ тот же (на Windows он и не включён по умолчанию: DLL
лежит рядом с `php.exe`, но `extension_dir` в сборке WinGet указывает на несуществующий `C:\php\ext`).

**Гейт теперь запускает лаунчер на любой ОС** — на Windows это боевой путь, на macOS доказательство,
что путь жив. Правило общее: проверка, которая «эмулирует» чужую ОС, обязана эмулировать **то самое
условие**; иначе она зелёная ровно там, где не работает.

## Гейт дистрибутива: две ложные тревоги и одна настоящая

- **CSS-сервер «не ответил»** — сервер отвечал; гейт читал первые 200 байт ответа, а признак
  `definitionProvider` стоит дальше (заголовок + длинный список возможностей). Порог поднят до 2000.
- **Адаптер PHP-отладки отсутствовал** — настоящая: `download.sh` упал на `curl` архива vsix
  (медленная сеть), а в отчёте это не было видно, потому что код выхода читался после `| tail`.
  Правило: код выхода конвейера — `${PIPESTATUS[0]}`, и после загрузки смотреть `ls` набора, а не
  последние строки лога. Повторный запуск скрипта идемпотентен.
- **Сравнение `.exe` и `.win.zip` сборка пропускает** («comparing .zip and .exe skipped in
  development mode»), хотя в исходниках оно есть. Поэтому инсталлятор проверяется тихой установкой
  (`/S /CONFIG=<silent.config> /D=<dir>`, шаблон конфига —
  `platform/build-scripts/resources/win/nsis/silent.config`) и сравнением с распакованным zip.
  **Каталог установки для проверки — короткий** (`D:\vi-test`): генератор списка файлов NSIS
  включает обход MAX_PATH (`\\?\`) только для каталогов, чей путь он *оценивает* длиннее 260,
  исходя из типичной длины каталога установки ≈113 символов (`NsisFileListGenerator.guessMaxPathLength`).
  Установка в каталог длиннее этой оценки молча теряет файлы в зазоре: в тестовый каталог на 129
  символов не доехали 27 файлов из `servers/node/node_modules`, при «Installation has been
  finished successfully» в логе. Это же ограничение касается пользователя, выбравшего очень
  длинный путь установки, — апстримное, не наше.
- **Windows-`unzip` и шаблон `extension/*`** — `*` там не пересекает `/`, и из vsix адаптера
  PHP-отладки распаковались четыре файла верхнего уровня без `out/phpDebug.js`. `download.sh`
  теперь распаковывает архив целиком во временный каталог и переносит подкаталог.
- **node с `2>/dev/null` не отвечает** — CSS-сервер и адаптер PHP-отладки при отброшенном stderr
  завершались, не записав ответ в stdout (четыре прогона: с `2>&1` ответ есть, с `2>/dev/null` —
  пусто). Гейт читает оба потока; проверке по подстроке лишние строки не мешают.
- **Фиксированная пауза плавает под нагрузкой** — при трёх параллельных проверках CSS-сервер не
  успевал стартовать за 5 с, stdin закрывался, и та же сборка получала красный гейт (три зелёных
  прогона и один красный). Теперь гейт держит stdin открытым и ждёт признак ответа до 20 с
  (`server_answers`), а не паузу; PowerShell-близнец с `Start-Sleep 4` валится на адаптере
  PHP-отладки по той же, по всей видимости, причине.
- **`wait` на убитом процессе под `set -e`** — возвращает 143 и роняет сам гейт без вердикта
  (поймано первым прогоном нового ожидания): после `kill` — `wait … || true`.

## Bazel на Windows

Тулчейн такой же герметичный: `./bazel.cmd` качает bazelisk и форк Bazel 9.1.0 JetBrains в
`%LOCALAPPDATA%\JetBrains\monorepo-bazelisk`, Bazel — 9.1.0-jb, output base `C:\ProgramData\_bazel`,
JBR — сам. Ни Developer Mode, ни привилегия на симлинки не понадобились. Visual Studio 2022 стоит на
машине, но cc-тулчейн сборке инсталлятора не нужен. Инсталлятор `.exe` собирает NSIS, который
сборка тоже качает сама; подпись пропускается, как и на macOS — SmartScreen на первом запуске
покажет «Windows защитила ваш компьютер», обход в заметках релиза. Первая сборка на медленной сети
(50–85 КБ/с): загрузка ~3000 внешних репозиториев ≈ 1,5 ч, компиляция ≈ 1 ч, упаковка 25 мин;
повторная сборка после правки набора серверов — только упаковка.

Запуск собранной IDE без следов в профиле пользователя: `IDEA_VM_OPTIONS=<файл>` с
`-Didea.config.path/-Didea.system.path/-Didea.log.path/-Didea.plugins.path` во временный каталог
(имя переменной — `envVarBaseName` из `product-info.json`, у нас унаследованное `IDEA`). Проверка —
строка `Loaded bundled plugins` в `idea.log` с четырьмя плагинами Vibe и LSP4IJ.
