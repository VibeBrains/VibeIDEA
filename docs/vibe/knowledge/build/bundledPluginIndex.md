# Плагин, скопированный в `plugins/`, не грузится: решает индекс

**[инцидент]**

## Контекст

31.08.2026, проверка собранного dmg на живом проекте. Переход к объявлению не работал даже на
константе того же класса (`self::PERIOD_COLUMN_VARIANTS`). Сперва это списали на отсутствие
Phpactor, потом на его слабость в динамике — обе версии оказались неверны.

Лог установленной IDE (`~/Library/Logs/VibeBrains/VibeIdea2026.3/idea.log`) сказал прямо:

```
plugin com.redhat.devtools.lsp4ij is not resolved
  └ dependent <depends> config 'vibe-lsp4ij-integration.xml' of plugin com.vibe.lsp excluded
```

**LSP4IJ не загружался ни в одной собранной сборке.** Значит описания серверов (`vibeVtsls`,
`vibePhpactor`, `vibeCss`, `vibeEslint`) не регистрировались никогда, и ни TypeScript, ни PHP через
LSP в дистрибутиве не работали вообще — при том что модуль компилировался, тесты были зелёными, а
файлы плагина лежали в `Contents/plugins/lsp4ij` и выглядели правильно.

## Суть

Если в дистрибутиве есть `plugins/plugin-classpath.txt` — а он есть всегда, — платформа грузит
встроенные плагины **только по этому индексу**
([`PluginDescriptorLoader.kt`](../../../../platform/core-impl/src/com/intellij/ide/plugins/PluginDescriptorLoader.kt),
поиск по `plugin-classpath.txt`). Каталог, скопированный в `plugins/` после генерации индекса,
для загрузчика не существует. Мы копировали LSP4IJ в `copyAdditionalFiles` — то есть после.

Штатный механизм для готовых плагинов — **`ProductProperties.getAdditionalPluginPaths()`**: сборка
копирует каталог И вписывает его в индекс (`generatePluginClassPathFromPrebuiltPluginFiles`).
Одна строка, но найти её надо ДО того, как половина продукта молча перестанет существовать.

Родственные грабли того же семейства — [threePackagingSystems.md](threePackagingSystems.md): состав
дистрибутива решают три независимых места, и `BUILD.bazel` среди них не тот, который отвечает за
упаковку.

## Продолжение того же дня: путь до встроенных файлов

Как только LSP4IJ загрузился, Phpactor упал с «Cannot run program "phpactor"»: наш поиск встроенного
phar смотрел в `PathManager.getPluginsPath()`, а это **пользовательский** каталог плагинов
(`~/Library/Application Support/…`), тогда как наши файлы лежат внутри установленного приложения.
Правильный адрес — путь САМОГО плагина (`PluginManagerCore.getPlugin(id)?.pluginPath`), он верен и
в установленной IDE, и при запуске из исходников; запасной вариант — `PathManager.getBundledPluginsDir()`.

Мораль та же, что у всего разбора: в среде разработки оба пути часто совпадают, и ошибка проявляется
только в дистрибутиве.

## Применение

**После каждой сборки читать в логе строку `Loaded bundled plugins`** и убеждаться, что там есть всё,
что мы туда клали. Не «файлы на месте» — файлы были на месте всё это время:

```bash
grep "Loaded bundled plugins" ~/Library/Logs/VibeBrains/VibeIdea*/idea.log | tail -1 | tr ',' '\n' | grep -iE "vibe|lsp4ij"
```

Пусто напротив ожидаемого имени — плагин не загружен, сколько бы его каталог ни весил.

Общее правило, вытекающее из трёх инцидентов одного дня (библиотека не доехала, висячие симлинки
уронили сборку, плагин не грузился): **юнит-тесты слепы к упаковке по построению** — они исполняются
там, где всё уже на classpath. Единственная проверка поставки — поставить и прочитать лог.
