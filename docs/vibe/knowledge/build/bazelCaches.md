# Кэши сборки Bazel: где лежат, откуда вторая база и как их переносить

**[инструмент+грабли]**

## Контекст

10.09.2026 VibeSweep, разбирая `~/Library/Caches` на машине владельца (32,4 ГБ), вышел на нашу
сборку: 26 ГБ кэшей Bazel на системном томе, и среди них две «сборочные базы» одного репозитория.
Разобрано 11.09.2026 командами на той же машине. В тот же день по решениям владельца все кэши Bazel
переехали на внешний том: утром disk cache, вечером весь `output_user_root`.

## Где что лежит и кто это задаёт

Пути задаёт апстримный `common.bazelrc`. Правка его была бы налогом на каждый синк, поэтому наш
код его не трогает, а машина переопределяет пути в `.bazelrc-user.bazelrc`:

| Строка `common.bazelrc` | Что | Апстрим, macOS | На машине владельца |
|---|---|---|---|
| 24 | `output_user_root`: базы сборки (`output_base`), install base, repository cache | `~/Library/Caches/JetBrains/MonorepoBazel` | `/Volumes/Storage/Caches/JetBrains/MonorepoBazel` |
| 54 | сборка мусора disk cache: `32G`, `28d` | — | как в апстриме |
| 55 | `disk_cache` — хранилище результатов действий по содержимому | `~/Library/Caches/JetBrains/monorepo-bazel-cache` | `/Volumes/Storage/Caches/JetBrains/monorepo-bazel-cache` |

`.bazelrc-user.bazelrc` подключается из `.bazelrc` (`try-import %workspace%/.bazelrc-user.bazelrc`,
строка 22) после `common.bazelrc` (строка 6) и лежит в `.gitignore` — это место апстрим сам отвёл
под настройки одной машины. У стартовой опции побеждает последнее значение, поэтому строка
`startup:macos --output_user_root=…` в нём перекрывает апстримную: `bazel info output_base
install_base repository_cache` после правки показал все три пути в новом корне.

Размеры 10.09.2026 (замер VibeSweep): repository cache 7,5 ГБ, две базы 4,8 и 4,2 ГБ, install base
177 МБ, disk cache 9,4 ГБ (CAS) + 46 МБ (action cache).

## Откуда вторая база — и почему это не «два написания пути»

`output_base` — это md5 от пути рабочей области:

```bash
md5 -qs /Volumes/Storage/Projects/VibeCode/VibeIDEA   # 0ca05161c29703e248ee14c11bb8f8a9
md5 -qs /Users/borodatych/Projects/VibeCode/VibeIDEA  # 7d650e28cc4547d2205ca16edec1348e
```

`~/Projects` — симлинк на `/Volumes/Storage/Projects`, и первое предположение было «проект открывают
то одним, то другим написанием». Проверка его опровергла: Bazel **сам разворачивает** путь рабочей
области. `bazel info output_base`, запущенный с `PWD=/Users/…`, вернул базу пути `/Volumes/…`
(`0ca05161…`), а `lock` старой базы не изменился. Два написания одной папки дают одну базу.

`7d650e28…` — **остаток переезда проекта**. Последняя команда в ней была 29.08 в 18:57 (время
`lock`), симлинк `~/Projects` создан 29.08 в 19:34, и через `/Users/…` после переезда Bazel не
запускали. Сама такая база не исчезнет: Bazel не знает, что пути, от которого она посчитана, больше
нет. Путь записан в её `DO_NOT_BUILD_HERE`.

## Как переносить корень, ничего не потеряв

Порядок, которым корень переехал 11.09.2026:

1. **`./bazel.cmd shutdown` — до правки настройки.** После правки та же команда уйдёт серверу
   нового корня, а сервер старого останется жить: у каждой базы свой сервер.
2. **Скопировать только repository cache** (`cache/repos`). Он адресован содержимым: файл
   `content_addressable/sha256/<хеш>/file` проверяется пересчётом хеша, а все 653 симлинка в нём
   относительные. 7,5 ГБ скопировались за 44 с (`rsync -a`); сверка — 41 253 записи совпали по пути,
   размеру и цели симлинка, 3129 файлов пересчитаны, расхождений нет.
3. **Базу сборки не копировать.** Внешние репозитории в ней — абсолютные симлинки в repo contents
   cache старого корня: из 2943 симлинков в `external/` 2938 указывают в
   `~/Library/Caches/JetBrains/MonorepoBazel/cache/repos/v1/contents/…`. Копия базы ссылалась бы в
   каталог, который удалят. install base Bazel распакует сам, база сборки создаётся заново.
4. **Строка в `.bazelrc-user.bazelrc`** и проверка `bazel info` — см. выше.
5. **Первая сборка — холодная.** Прежнего disk cache к тому времени уже не было, и
   `//vibe-plugins/vibe-agent:vibe-agent` собирался с нуля: 535 действий (1 из disk cache, 288 в
   воркерах, 159 в песочнице), 4 мин 25 с на Mac mini M4 с 16 ГБ. Почти всё это время — критический
   путь (4 мин 9 с), то есть цепочка компиляций крупных модулей платформы.
6. **Старый корень удаляет владелец**, и простым `rm -rf` его не взять: Bazel оставляет каталоги
   только для чтения (246 штук, например python-тулчейн из `rules_python`). Команда:
   `chmod -R u+w ~/Library/Caches/JetBrains/MonorepoBazel && rm -rf ~/Library/Caches/JetBrains/MonorepoBazel`.

Симлинк вместо настройки не годится. Жёсткой ссылки на каталог macOS не даёт, а между томами
жёстких ссылок нет вовсе. Симлинк при отпавшем диске даёт `ENOENT` на запись и `EEXIST` на `mkdir`,
и работа встаёт до возвращения диска (проверено VibeSweep).

## Spotlight: внешний том индексируется, `~/Library/Caches` — нет

Переезд из `~/Library/Caches` меняет не только диск. Spotlight в `~/Library/Caches` не заглядывает:
`DO_NOT_BUILD_HERE` старой базы в индексе не найден. Внешний том он индексирует (`mdutil -s
/Volumes/Storage` — «Indexing enabled»): файл disk cache нашёлся по имени, скопированный кэш попал в
индекс за минуты, а во время холодной сборки в индексе было уже 56 643 из 88 283 файлов нового
корня; `mds_stores` в снимке `top` — около 10 % процессора.

Лечится исключением папки целиком: Системные настройки → Spotlight → «Конфиденциальность» → «+»
(«Добавить папку или диск для исключения») → `/Volumes/Storage/Caches`. Это системная настройка, её
ставит владелец. Переименование в `*.noindex` отвергнуто: оно меняет пути и повторяется для каждого
кэша, а исключение `Caches` целиком повторяет то, как система обходится с `~/Library/Caches`.
Проверка: `mdfind -onlyin /Volumes/Storage/Caches/JetBrains -name DO_NOT_BUILD_HERE` — пусто.

Грабли замера: запрос `mdfind 'kMDItemFSName == "*"'` возвращает 0 даже в проиндексированной
папке. Считать надо `kMDItemContentTypeTree == "public.item"` или искать по имени (`-name`), и
сперва проверять запрос на папке, которая точно в индексе.

## Замер: на внешнем томе сборка почти не медленнее

Прежний совет VibeSweep от 10.09 — «`output_base` оставить на внутреннем диске: тысячи мелких
файлов под компилятором, перенос заметно замедлит сборку». На этой машине его проверили замером:
Mac mini M4, внешний том NVMe по PCI-Express (APFS), исходники и так лежат на нём. Сравнивались два
корня на одной цели `//vibe-plugins/vibe-agent:vibe-agent`, при общем disk cache и одном живом
сервере за раз. Каждая правка — уникальный комментарий в одном файле, чтобы действие не попало в
кэш.

| Что мерили | Внешний том | Внутренний диск |
|---|---|---|
| Правка → пересборка, сервер прогрет (три прогона) | 3,9 / 2,8 / 2,6 с | 2,8 / 2,8 / 2,7 с |
| Первая сборка после старта сервера, без правки (поочерёдно) | 9,6 и 7,6 с | 7,8 и 7,3 с |
| Первая сборка после старта сервера, с правкой (поочерёдно) | 14,2 и 11,3 с | 11,9 и 10,6 с |

- **Ежедневная пересборка — одинаковая.** Время самой компиляции (критический путь) на обоих томах
  одно и то же: 2,5–3,6 с.
- **Старт сервера на внешнем томе дороже на 0,3–2,3 с.** Лишнее время — вне компиляции: загрузка,
  анализ и проверка 533 действий по кэшу действий, то есть как раз работа с множеством файлов.
  Платится раз на запуск сервера, а не на сборку. В замерах с правкой `mds` на внешнем томе был в
  нуле — разница не от Spotlight.
- **Выброс 27,7 с** (прогрев сразу после холодной сборки, критический путь 19,5 с) в четырёх повторах
  не повторился — похоже, первый запуск воркера в свежем корне.
- Тесты `vibe-agent` в новом корне: 1585, падений нет, один пропущен (живой тест голоса без модели).

Цена переезда — одна холодная сборка, пара секунд на каждый старт сервера и индексация Spotlight,
пока нет исключения. Вывод касается этой машины и этого диска: на медленном внешнем диске замер
надо повторить, прежде чем переносить базу сборки.

Вложенная рабочая область `platform/build-scripts/bazel` (генератор jps-to-bazel) задаёт
`output_user_root` в своём `.bazelrc`, а наш `.bazelrc-user.bazelrc` не читает: её запуск создаст
корень в `~/Library/Caches/JetBrains/MonorepoBazel` заново. В нашей работе она не участвует.

Прежнего disk cache (9,6 ГБ) и базы-сироты `7d650e28…` (4,8 ГБ) на диске уже нет — их удалил
владелец.

## Применение

- Новый машинный путь — только в `.bazelrc-user.bazelrc`, никогда в `common.bazelrc`.
- Переезд корня: сперва `shutdown`, копировать только repository cache, базу сборки — никогда.
- Кэш на внешнем томе — сразу исключить из Spotlight: у `~/Library/Caches` это есть по умолчанию.
- После переезда проекта или смены пути рабочей области ищите базы-сироты: у каждой в
  `DO_NOT_BUILD_HERE` записан путь, от которого она посчитана. Если такого пути больше нет, база
  лишняя.
- Правило «база-сирота» передано VibeSweep (`sessions/bazel-stale-output-base.md` в его памяти): чистильщик
  диска должен узнавать кэш Bazel и называть строку настройки, а не предлагать симлинк.
