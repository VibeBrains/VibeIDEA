# Страницы настроек: `Configurable.NoScroll` — обещание, которое надо выполнить

**Дата:** 2026-08-24 (двойной скролл) и 2026-08-28 (обрезанная страница) · **Ветка:** next

## Две ошибки, зеркальные друг другу

Платформа сама оборачивает `Configurable` в скролл — если страница не помечена
`Configurable.NoScroll`. Отсюда две ловушки, и мы наступили на обе:

1. **Свой скролл без маркера → двойной скролл** и горизонтальная полоса: платформенная обёртка
   меряет содержимое по неперенесённой ширине html-подсказок и растягивает вьюпорт. Лечится
   маркером `NoScroll` (Провайдеры/Модели, 2026-08-24).
2. **Маркер без своего скролла → страницу просто обрезает** по нижнему краю окна, скроллить
   нечем. Так уехали настройки «Агента»: под «Таймаут рукопожатия» уходило ещё несколько полей,
   а пользователь их не видел (2026-08-28, нашёл владелец).

Правило: **`NoScroll` не «страница без скролла», а «скролл делаю я сам»**. Пометил маркером —
верни `JBScrollPane(TracksViewportWidthPanel(form))`; форма длиннее диалога почти всегда.

`TracksViewportWidthPanel` (`Scrollable` с `getScrollableTracksViewportWidth() = true`) — вторая
половина рецепта: без неё html-подсказки не переносятся по ширине и возвращают ту самую
горизонтальную полосу, ради которой маркер и ставился.

## Почему на это нет юнит-теста

Проверка «страница с `NoScroll` возвращает `JScrollPane`» требует платформенных зависимостей
(`Configurable`, Swing-компоненты) в тестовом модуле, который у нас намеренно лёгкий — чистые
юнит-тесты без IDE-окружения, миллисекунды на прогон. Тянуть туда `ide-core` ради одной проверки
дороже, чем стоит сама проверка. Поэтому правило живёт здесь и в комментариях трёх страниц;
при добавлении новой страницы настроек — сверяйся с этой записью.
