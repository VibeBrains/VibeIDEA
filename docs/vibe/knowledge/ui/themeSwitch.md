# Смена темы мимо `DarculaInstaller`: тёмная тема со светлым диалогом

**Дата:** 19.09.2026 · **Ветка:** next · **Статус:** правило + гейт

## Симптом

На живой 0.6.17 владелец выбрал на нашей странице «Оформление» тему Vibe Graphite.
Окно проекта стало графитовым — дерево, редактор, панели.
Диалог настроек, в котором он это сделал, остался **белым целиком**: фон, дерево разделов, переключатели.

Юнит-тесты зелёные, восемь гейтов зелёные, цвета из json темы применились правильно.
Видно дефект было только глазами.

## Причина

Страница переключала тему своей парой строк:

```kotlin
manager.setCurrentLookAndFeel(info, false)
manager.updateUI()
```

`setCurrentLookAndFeel` ставит тему и схему редактора — и на этом всё
(`LafManagerImpl.setLookAndFeelImpl`).
Переключение светлого на тёмное делает **другой** класс — `DarculaInstaller`, и делает он ровно две вещи:

```java
JBColor.setDark(dark);
IconLoader.setUseDarkIcons(dark);
```

Зовёт его только платформенный вход `QuickChangeLookAndFeel.switchLafAndUpdateUI` — тот самый,
которым пользуется платформенная страница оформления (`AppearanceConfigurable`).

Ключевое здесь — что `JBColor.DARK` это **кэш**:

```java
private static final SynchronizedClearableLazy<Boolean> DARK =
  new SynchronizedClearableLazy<>(() -> StartupUiUtil.INSTANCE.isDarkTheme());
```

Он вычисляется один раз при старте IDE и сбрасывается **только** через `setDark`.
Поэтому после нашего переключения каждая пара `JBColor(светлый, тёмный)` и каждый значок
продолжали отдавать сторону ПРЕЖНЕЙ темы — сколько бы раз ни звался `updateUI()`.

Отсюда и расслоение, которое выглядит необъяснимым:
цвета, приходящие из json темы через `UIManager`, — тёмные (окно проекта),
цвета, собранные парами `JBColor`, — светлые (диалог настроек).

## Правило

**Тему в нашем коде переключает только платформенный вход.**

```kotlin
QuickChangeLookAndFeel.switchLafAndUpdateUI(manager, info, /* async = */ false)
```

Он делает всю последовательность: снимок для анимации, `DarculaInstaller.install()`/`uninstall()`,
ровно один `updateUI()` (без двойного — двойной даёт NPE в части компонентов), уведомление слушателей.

Прямой `LafManager.setCurrentLookAndFeel` в наших исходниках запрещён.

## Гейт

`checkVibeUi.sh`, раздел 8ж — в обе стороны:

- вызов `setCurrentLookAndFeel` в наших `.kt` (кроме комментариев и тестов) валит гейт;
- если наш код опирается на `switchLafAndUpdateUI`, метод обязан существовать в платформе —
  синк с апстримом не должен унести его молча.

Проверен подкладыванием настоящего нарушения: со старым вызовом гейт падает, с новым — зелёный.

## Чему это учит

Шестой случай за два дня из одной семьи: **гейт, проверяющий форму вызова, зеленеет на сломанном результате.**

Здесь он был зелёным потому, что проверять было нечего: сломанным был шаг, которого у нас не было вовсе.
Отсюда практическое следствие — когда мы повторяем своим кодом то, что платформа делает своим входом,
надо не «сделать то же самое», а **звать её вход**: в нём окажутся шаги, о которых мы не знаем.

Соседние дефекты той же страницы, найденные этим же разбором:

- подсказка страницы обещала «Выбор применяется по кнопке „Применить"», хотя тема применяется сразу
  по щелчку с 19.09 — строку не поправили вместе с поведением;
- флажок «Следовать светлой и тёмной теме системы» писался в тот же миг, не входил в `isModified`
  и не возвращался «Отменой»;
- при включённом автодетекте список тем оставался живым, хотя выбор из него не переживает
  ближайшей смены светлого на тёмное (платформа свой список в этом случае гасит).
