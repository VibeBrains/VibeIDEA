# `platform/lsp` против LSP4IJ: что выбрать под языки

**[архитектура]**

## Контекст

Пункт роадмапа «отслеживать `platform/lsp` как нативную замену LSP4IJ» заведён при основании форка,
когда модуль был закрыт. Проверено 01.09.2026 на свежей базе (`320ed57059`) — **фактами из дерева и
собранного дистрибутива**, а не по документации.

## Что выяснилось

**Модуль открыт, лежит в нашем дереве и УЖЕ ЕДЕТ в дистрибутив.** 60 исходников под Apache 2.0,
`intellij.platform.lsp.jar` (466 КБ) и `intellij.platform.lsp.impl.jar` (2 МБ) в `Contents/lib`
нашей сборки. Точка входа — `LspServerSupportProvider` (extension point), дескриптор сервера —
`LspServerDescriptor`. API не помечен ни `@Experimental`, ни `@Internal` (0 упоминаний в
`api-dump.txt`; экспериментального API отдельно — 6 строк).

**Возможности покрыты широко** — 31 кастомайзер: переход к определению, к типу, к реализации, поиск
использований, автодополнение, диагностика, hover, форматирование (в том числе по набору),
переименование, code actions, inlay hints, семантическая подсветка, подсказка сигнатуры, иерархии
вызовов и типов, символы документа и рабочей области, свёртка, ссылки, цвета.

**Чего нет — DAP в открытой части.** В intellij-community модуля отладочных адаптеров нет:
`DebugAdapterSupportProvider` в дереве не находится (`git grep` пуст, сверено 11.09.2026), в
`platform/lsp/src` упоминаний нет. В закрытой части платформы DAP есть с 2024.2 — задача
[IJPL-83441](https://youtrack.jetbrains.com/issue/IJPL-83441) решена 21.06.2024. То есть DAP у
JetBrains существует, но не в открытом дереве, из которого собираемся мы. Отладка TS и PHP у нас
держится на DAP-стороне LSP4IJ.

## Вывод

Замена LSP4IJ на `platform/lsp` **возможна и выглядит правильной для языковых фич**: минус
сторонний плагин (EPL-2.0) в дистрибутиве, минус его собственный жизненный цикл и настройки, плюс
родные виджет статуса и интеграция.

Но она **не бесплатна и не полна**:

- переписываются четыре наши фабрики (`vtsls`, `phpactor`, `css`, `eslint`) с модели
  «`server` + `fileNamePatternMapping` в XML» на `LspIntegrationProvider`;
- **LSP4IJ придётся оставить ради DAP** — иначе отладка исчезнет; то есть выигрыш «минус плагин» не
  достигается, пока DAP не появится в открытой части платформы;
- **пропадают файловые операции LSP** (см. ниже) — правка импортов при переносе файла;
- поведение придётся перепроверять целиком: гейт дистрибутива проверяет запуск серверов, но не то,
  как IDE показывает их находки.

**Решение (01.09.2026, подтверждено решением №73 от 10.09.2026): не мигрировать сейчас.**
Переписать интеграцию, оставив в дистрибутиве тот же LSP4IJ ради отладки, — это работа без
выигрыша. Пункт переводится из «отслеживать» в условие: **мигрируем, когда DAP-модуль окажется в
intellij-community** либо когда мы осознанно откажемся от отладки через адаптеры (или когда LSP4IJ
сломается на обновлении платформы).

## Применение

Проверять при каждом синке с апстримом, появился ли DAP в открытом дереве. Одна команда — сторож
по классу точки расширения, а не по имени каталога: каталог могут назвать как угодно, а класс
провайдера DAP-модуль принесёт с собой:

```bash
git grep -l DebugAdapterSupportProvider
```

Пусто — ждём. Нашлось — пункт роадмапа оживает, и миграция становится осмысленной.

## Что изменилось к 09.09.2026 (сверено с заметками API платформы)

Решение прежнее — **не мигрировать**, DAP в открытой части так и нет.

Платформенный LSP получил в 2026.1 Range Formatting (`textDocument/rangeFormatting`), Code Lens
(`textDocument/codeLens`) и Optimize Imports (через `textDocument/codeAction` вида
`source.organizeImports`), плюс переписанную ради производительности подсветку
([api-notable-list-2026](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2026.html)).
Механизм — не миксины к дескриптору, а customizer-классы: `platform/lsp/src/api/customization/
LspCodeLensCustomizer.kt`, `LspOptimizeImportsCustomizer.kt` и соседние. **Поправка 11.09.2026:**
code lens и range formatting выигрышем переезда не считаются — у LSP4IJ они есть и сегодня; из
трёх возможностей новой для нас остаётся разве что Optimize Imports, и та не проверена.

**И одно ломающее, которое станет ценой миграции, а не её выгодой:** в 2026.1.4 `LspServerManager`
переименован в `LspClientManager` и зарегистрирован ТОЛЬКО под новым интерфейсом — обращение по
старому имени возвращает `null`, а не ошибку компиляции. Кастомизация переехала с
`LspServerDescriptor.lspCustomization` на `LspClientDescriptor.lspCustomization`.

Наша база — линия 263, то есть 2026.3: оба изменения у нас **уже внутри**, просто не задевают нас,
пока языки идут через LSP4IJ.

## Что изменилось к 11.09.2026 (сверено с блогом, списком изменений API и деревом)

- **API клиента открыт для продуктов на открытой кодовой базе**, работа начата в 2026.1.4; в 2026.2
  переименования `LspServer` → `LspClient`, провайдер → `LspIntegrationProvider`
  ([блог](https://blog.jetbrains.com/platform/2026/06/open-sourcing-the-lsp-client-api-in-intellij-idea-2026-2/)).
  Про DAP в посте ни слова.
- **В списке ломающих изменений по LSP одна запись** — 2026.1 (`LspServerManager` →
  `LspClientManager`); в 2026.2 и 2026.3 записей по LSP нет
  ([api-changes-list-2026](https://plugins.jetbrains.com/docs/intellij/api-changes-list-2026.html)).
- **Цена переезда выросла на одну потерю: файловые операции LSP.** Греп по `platform/lsp/src` на
  `fileOperations`, `willRenameFiles`, `didRenameFiles` пуст; у LSP4IJ для этого есть
  `FileOperationsManager`. vtsls объявляет `didRename`, поэтому при переезде, скорее всего, пропадёт
  правка импортов при переносе файла. Живьём не прогонялось — при пересмотре проверить первым.
- **Условие (а) решения №73 уточнено**: не «в платформе появится DAP» (он там есть, в закрытой
  части), а «DAP-модуль открыт в intellij-community» — со сторожем `git grep -l
  DebugAdapterSupportProvider`.
