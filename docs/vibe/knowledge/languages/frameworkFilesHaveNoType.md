# Языковой сервер без типа файла — половина поддержки
← [Knowledge Index](../README.md)

## [грабли+решение] `.vue`, `.sass` и `.styl` открывались «неизвестным файлом»

**Роль:** [грабли] · **Найдено:** 18.09.2026, разведкой перед поддержкой Vue/Svelte/Astro

## Контекст

18.09.2026 в 0.6.11 уехали серверы для `.sass` (Some Sass) и `.styl` (stylus-lsp) — языков,
которых в открытой платформе нет вовсе. Работа считалась законченной: сервер зарегистрирован,
сопоставление в XML есть, гейты зелёные.

Разведка перед следующим языком показала, что сделана половина.

## Суть

**Языковой сервер и тип файла — две разные вещи, и платформа не выводит одно из другого.**

LSP4IJ сопоставляет сервер с файлом по шаблону имени, и это работает. Но редактор открывает файл
по ТИПУ, а тип платформа берёт из своих деклараций и из TextMate-грамматик. Проверено командой:

```
grep -rn 'extensions="[^"]*styl' --include="*.xml" platform/ plugins/   → пусто
ls plugins/textmate/lib/bundles/ | grep -iE "vue|svelte|astro|sass|stylus"  → только scss
```

То есть ни `.vue`, ни `.svelte`, ни `.astro`, ни `.sass`, ни `.styl` платформе не известны никак.
Такой файл открывается «неизвестным типом»: предложение выбрать тип вручную и ноль подсветки.
Подсказки от сервера при этом приходят — и именно поэтому дефект не виден изнутри: разработчик
проверяет то, что делал (переход, автодополнение), и не смотрит на цвет.

**Юнит-тест этого не увидит по построению.** Он проверяет наши данные — реестр серверов, XML,
команды. Вопрос «есть ли у платформы тип для этого расширения» задаётся не нашему коду.

## Решение

У платформы TextMate есть публичная точка расширения `com.intellij.textmate.bundleProvider`
(интерфейс `TextMateBundleProvider`, `dynamic="true"`). Плагин отдаёт ей свои бандлы путями на
диске — и этого достаточно: тип файла объявляет сама грамматика через `contributes.languages`,
отдельная регистрация `<fileType>` не нужна.

Важные частности:

- **Бандлы едут ФАЙЛАМИ рядом с плагином, а не ресурсами в jar.** Точка расширения принимает
  `java.nio.file.Path`, а у ресурса внутри архива пути нет. Кладём туда же, куда языковые серверы
  (`plugins/vibe-lsp/textmate`), тем же копированием в `bundleExternalPlugins`.
- **`scopeName` берётся ИЗ грамматики, а не пишется руками.** Манифест бандла собирает скрипт
  `deps/textmateBundles.py`: скопированное руками имя области однажды разойдётся с файлом, и
  разойдётся молча — подсветка просто не включится.
- **Язык объявляет только основная грамматика.** У Vue их пять (сам компонент плюс четыре
  вложенных области); объявленный на вложенной язык дал бы тип файла без единого расширения.
- **Зависимость от плагина TextMate — необязательная** (`<depends optional="true">`): сервер без
  подсветки полезен, подсветка без сервера тоже, связывать их судьбы незачем.

## Применение

- **Новый язык, которого нет в платформе, — это ДВЕ работы, а не одна:** сервер (смысл) и
  грамматика (цвет и тип файла). Сделана одна — возможность заявлена наполовину.
- **Проверка — не тестом, а гейтом дистрибутива:** `checkVibeDist.sh` требует бандл на месте, все
  объявленные в манифесте грамматики файлами, объявленный язык и NOTICE с лицензиями; отдельно
  сверяет список имён у провайдера со списком каталогов в образе.
- **Смотреть на цвет.** Признак, по которому дефект видно за секунду: файл открылся чёрно-белым.

## Лицензии

Грамматики берутся одним закреплённым пакетом `tm-grammars` (сборник проекта shiki): пять
грамматик из пяти чужих репозиториев, с NOTICE, где у каждой назван источник и лицензия. Пакет
проверяется по sha256, как LSP4IJ и Phpactor.

Отдельная грабля: в NOTICE грамматика Sass помечена `NOASSERTION`. Проверено у источника
18.09.2026 — репозиторий `TheRealSyler/vscode-sass-indented` объявляет MIT и текстом лицензии, и
полем `license` в `package.json`; сканер не разобрал шапку «The MIT License (MIT)». Метка
автоматического сканера — повод сходить к первоисточнику, а не вывод.

## Как это проверялось (и две ловушки проверки)

**Класс из content-модуля — не то же самое, что класс из чужого плагина.** Гейт дистрибутива
справедливо не поверил на слово: `TextMateBundleProvider` лежит не в главном jar плагина TextMate,
а в его content-модуле (`lib/modules/intellij.textmate.jar`), и наш случай отличался от LSP4IJ,
где класс в главном jar. Проверено ЗАПУСКОМ собранного образа 0.6.12 с
`idea.log.debug.categories=#org.jetbrains.plugins.textmate`: в логе 69 строк «Bundle from …» при
64 платформенных, пять наших — из `plugins/vibe-lsp/textmate/`. Обычного `<depends optional="true">`
оказалось достаточно; городить свой content-модуль не понадобилось.

**vtsls не рассылает ПУСТОЙ список диагностик.** На стенде «импорт `.vue` в обычном `.ts`»
поведение выглядело так: без плагина tsserver приходит «Cannot find module './Hello.vue'», а с
плагином — тишина. Тишина читалась как «сервер умер», и полчаса ушло на поиск несуществующей
поломки. Правда была в собственном логе tsserver (`typescript.tsserver.log: verbose`, файл
называется в `window/logMessage`): `semanticDiag` отработал и вернул `diagnostics: []` — то есть
ошибок нет, а клиент просто не стал пересылать пустоту.

Отсюда правило для всех будущих стендов по языковым серверам: **отсутствие сообщения не является
ответом.** Вердикт берётся из положительного признака — ответа на запрос или строки в логе самого
сервера, — а не из того, что чего-то не пришло.

**Ещё одна мелочь того же стенда:** vtsls запрашивает настройки `workspace/configuration` с ПУСТОЙ
секцией, то есть просит весь объект целиком. Разбор, который ищет в настройках ключ с пустым
именем, вернёт ему `null`, и настройка молча не доедет.
