# Навигация LSP: что мы можем поправить, а что живёт в чужом плагине

**Дата:** 18.09.2026 · **Повод:** «неглубоко интегрирован?» — всплывашка `LSP Symbol "encodeURIComponent"`

## Откуда берётся надпись

Не из платформы и не из нашего кода: строка `usage.description=LSP Symbol` лежит в
`messages/LanguageServerBundle.properties` внутри **LSP4IJ** (`lsp4ij-0.20.2.jar`), который мы
поставляем как готовый плагин. Отвечает на вопрос «что это за элемент» их
`LSPUsageElementDescriptionProvider`.

## Что сделано

Свой `ElementDescriptionProvider` с `order="first"`: их провайдер отвечает ВСЕГДА, поэтому встать
после него значит не ответить никогда. Мы отвечаем «символ TypeScript (vtsls)» — язык берётся у
того же сопоставления имён файлов серверам, которое выбирает сам сервер.

## Чего сделать нельзя, не тронув чужой плагин

**Подчёркивание всего подряд.** Решение «этот идентификатор навигабелен» принимает LSP4IJ, и его
`LSPDeclarationFeature.isSupported` — это вопрос про ФАЙЛ, а не про позицию в нём. Спросить сервер
про каждое слово под курсором в этом API негде.

**Сигнатура вместо слова «символ».** Она приходит от сервера запросом `textDocument/hover`, а
описание элемента платформа спрашивает синхронно на EDT. Ждать сервер в этот момент — подвесить
редактор на каждое наведение мыши. Правильное место — документация (`DocumentationTarget`), и это
отдельная задача, а не правка подписи.

## Развилка для владельца

Либо мы живём с подчёркиванием LSP4IJ, либо пишем свой слой навигации поверх нашего же LSP-клиента
и перестаём зависеть от их `GotoDeclarationHandler`. Второе — большая работа, и браться за неё
стоит вместе с документацией по наведению, а не отдельно.

## Свой слой навигации: как он устроен (19.09.2026)

Развилка закрыта решением: **свой слой, форк LSP4IJ не берём.** Форк чужого плагина означал бы
свой конвейер его сборки и налог при каждом их выпуске, а нужного вопроса в их API нет по
построению — `isDefinitionSupported(PsiFile)` спрашивает про ФАЙЛ, а не про позицию.

Четыре части, и ни одна не работает без остальных:

1. **`nav/LspDefinitionCache`** — чистые правила и состояние, без платформы. Три из них держат всю
   возможность: промах — это «не знаю», а не «нет» (иначе запроса не будет и не подчеркнётся
   никогда); ответ не переживает правку документа (иначе смещение отвечает за другое место);
   запрос не уходит дважды и не запирает позицию, если сервер упал. Восемь тестов.
2. **`nav/VibeLspNavigation`** — единственное место встречи правил с протоколом: перевод типов и
   асинхронный `textDocument/definition` через `LSPDefinitionSupport(PsiFile)`. Ответ сервера
   бывает в двух формах, `Location` и `LocationLink`, и разбирать надо обе — иначе часть серверов
   «молча ничего не находит».
3. **`nav/VibeLspGotoDeclarationHandler`** — отвечает из кэша мгновенно, промах заводит запрос и
   честно не подчёркивает. Цель — `FakePsiElement` с дескриптором открытия, тот же приём, что в
   переходе по Ext JS, и по той же причине: PSI у файлов на сервере нет.
4. **`nav/PreciseNavigation`** — выключает переход LSP4IJ у наших фабрик. Без этого пункта первые
   три бесполезны: решение «подчеркнуть» принимает ЛЮБОЙ обработчик, вернувший цель, и пока их
   отвечает «да» на весь файл, наша точность не меняет ничего.

**Выключатель обязателен.** Ключ реестра `vibe.lsp.precise.navigation`, по умолчанию выключен:
замена навигации меняет то, что человек видит под курсором в каждом файле, и проверить её можно
только руками. Ключ даёт вернуться к прежнему поведению, не пересобирая IDE.

**Грабля, найденная до запуска:** сервер отдаёт URI с процентным кодированием, платформа хранит
URL без него. `file:///Мои%20файлы/a.ts` и `file:///Мои файлы/a.ts` — один файл, но по первому
платформа не найдёт ничего, и симптом обманчив: сервер ответил правильно, цель есть, а переход «не
работает». Первая версия приведения URI у меня была пустышкой — писал по догадке, а не по факту.

**Чего этот слой не делает:** сигнатуру из `hover` вместо слова «символ». Она приходит запросом, а
описание элемента платформа спрашивает синхронно на EDT; правильное место — документация
(`DocumentationTarget`), и это отдельная задача.
