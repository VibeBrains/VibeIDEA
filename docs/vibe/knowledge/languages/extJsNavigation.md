# Навигация по Ext JS без JS-ядра

**Повод (владелец, 12.09.2026).**
В открытом на Windows файле `Ext.define('common.MorbusOnko….ExecModal', { extend: 'common.MorbusOnko….BaseModal' … })`
Ctrl+Click по имени родителя ничего не делал.
В PhpStorm то же самое работает.

## Почему в PhpStorm работает, а у нас не работало

PhpStorm понимает Ext JS не сам по себе, а через **закрытый плагин JavaScript** вендора: там есть парсер JS,
индекс символов и отдельная поддержка `Ext.define`.
В intellij-community JS-ядра нет вовсе — это часть Ultimate.
Наш `tsserver` тоже не помощник: для него `'common.…BaseModal'` — просто строковый литерал, а не ссылка.

То есть это была не поломка, а отсутствующая возможность, и закрывать её пришлось своими средствами.

## Главное ограничение: PSI нет

`.js` у нас показывает TextMate, PSI файла плоское.
Отсюда два следствия, определившие всю конструкцию:

**Ссылки вешать не на что.**
`PsiReferenceContributor` требует дерева, которого нет.
Работает только `gotoDeclarationHandler`: ему достаточно редактора и позиции курсора, а текст документа он читает сам.

**Цель перехода приходится делать руками.**
Вернуть «элемент на нужном смещении» неоткуда, а возврат `PsiFile` привёл бы в начало файла —
для файла на тысячу строк это равносильно отсутствию перехода.
Решение — `FakePsiElement`, который в `navigate()` открывает `OpenFileDescriptor(project, file, offset)`.

## Разбор по тексту — сознательное решение

Объявления ищутся регулярным выражением по содержимому файла, а не парсером.
Цена названа прямо: имя класса, собранное из переменных, найдено не будет, а имя внутри комментария — будет.
Для навигации это приемлемо: худшее следствие — лишний вариант перехода, а не испорченный файл.
Альтернативой был свой парсер JavaScript, и он стоит несопоставимо дороже задачи.

Индексируются и `Ext.define('…')`, и `alias`/`xtype`: из разметки класс ищут именно по псевдониму.
Родительский класс из `extend` в индекс **не** попадает — это ссылка, а не объявление.

## Почему индекс, а не поиск при клике

У владельца кодовая база медицинской системы с тысячами объявлений.
`FileBasedIndex` держит карту «имя → смещение» и переживает перезапуск;
перебор файлов на каждом Ctrl+Click был бы заметен рукам.
Фильтр входа — по расширению `.js`, а не по типу файла: в открытой платформе `.js` достаётся то TextMate,
то простому тексту, и привязка к типу разошлась бы с реальностью на первой же настройке пользователя.

**Версию индекса поднимать при каждой правке разбора** — иначе у тех, кто уже открывал проект,
останется карта, собранная старым кодом.

## Что нашла проверка на живой платформе

Чистые тесты разбора были зелёными, а первый же тест на настоящем проекте упал:
цель перехода знала своё смещение только внутри `navigate()`, а `getTextOffset()` у `FakePsiElement`
по умолчанию возвращает `0`.
Платформа спрашивает именно его — по нему рисуется предпросмотр и выбирается строка в списке,
когда объявлений найдено несколько.
Лечится переопределением `getTextOffset()` и `getTextRange()`.

Второе вылезло только там же: **тест, открывающий редактор, поднимает и соседний LSP4IJ**,
а тот на старте лезет в `lsp4j-jsonrpc`.
Без этой банки в classpath теста падает любой наш тест на платформе, и падение выглядит чужим.
Обе банки прописаны в `runtime_deps` тестовой цели.

Вывод общий, не про Ext JS: **чистые тесты не заменяют одного теста на платформе**.
Разбор они проверяют полностью, а контракт с платформой — не видят по построению.

## Гейт

`ExtJsTest` — на образце с экрана владельца: класс и псевдоним считаются объявлениями, `extend` — нет,
смещение указывает на само имя, литерал под курсором не ищется через перенос строки,
а имя без точки классом не считается (иначе в цель перехода превратилась бы каждая строка кода).

## Второй шаг: методы, config и события (13.09.2026)

**Повод.** Владелец: «прыгает по TypeScript, а по ExtJS — только по именам классов».
Не работали короткий `xtype: 'grid'` при `alias: 'widget.grid'`, `this.метод` из родителя, `callParent`,
геттеры конфигов и события.

**Регулярных выражений стало мало.** Для методов нужно тело класса: где начинается и кончается объект
`Ext.define`, его ключи, родитель. Полный парсер JavaScript по-прежнему не нужен — хватает токенизатора,
который знает строки, комментарии, шаблонные и regex-литералы, и глубины скобок.
Побочный выигрыш: `Ext.define` внутри комментария больше не считается объявлением.

**Грабля regex-литерала.** `/` после `(`, `,`, `=` и `return` — начало регулярного выражения, после `)`, `]`,
идентификатора — деление. Без этого различения `/[}{]/` в рендерере колонки закрывал тело класса раньше времени.

**Четыре индекса на одно чтение файла.** Объявления (с коротким xtype), структура классов, методы по имени,
события. Разбор кэшируется на индексируемом содержимом (`UserData`), поэтому четыре индекса стоят одной токенизации.

**Порядок поиска члена:** сам класс, затем примеси, затем `extend` — поиском в ширину с потолком классов, чтобы цикл
в иерархии не повесил клик. `callParent` ищет от родителя. Геттер ищется сначала как явный метод, потом как ключ `config`.

**Неизвестный получатель** (`store.load()`) — все методы с этим именем, но не больше двадцати: `load` и `create`
встречаются сотнями, и список из сотни целей хуже отсутствия перехода.

**Минифицированный код не индексируется:** `*.min.js` по имени, остальное — по строке длиннее 5000 символов.
Иначе `ext-all.js` превращает каждое короткое имя в мусорную цель. Отладочная сборка фреймворка с нормальными строками
индексируется — по ней переход ведёт в исходник `Ext.grid.Panel`.

**Индексы смотрят и в библиотеки** (`allScope`), события — только в проект: событие фреймворка вроде `click`
встречается тысячи раз.

## Третий шаг: псевдонимы this и свойства по цепочке (14.09.2026)

**Повод.** Владелец на рабочем проекте: Ctrl+Click по `spinnerInteger` в `constants.NumberConfigs.spinnerInteger` дал «No usages found».
И замечание к объяснению: псевдонимов `this` в коде много — `me`, `win`, `scope`, `_scope`, `_this`, `_ths`, `ths`, — «все перечислять будешь?».

**Список имён — неверный путь.** Он всегда отстаёт на следующее имя.
Псевдоним читается из кода: в методе под курсором ищется `X = this` (с `var`, `let`, `const` или без).
`X = this.up('window')` — другой компонент, не класс: за `this` идёт точка, такое присваивание не считается.
`a == this` — сравнение, а не присваивание: перед `this` стоит второй `=`.
Часть имён из списка владельца (`win`, `scope` как параметр) — вовсе не `this`; для них честный путь — поиск по имени, а не притворство.

**Индекс хранил только методы** — сознательно, против шума, и именно поэтому свойство-константа не находилось.
Теперь индекс членов хранит методы и свойства (`ExtMemberIndex`, версия индекса 3); `config`-ключи остаются отдельными.

**Цепочка `A.B.член`.** Имя класса у места использования почти никогда не пишется полностью: `constants.NumberConfigs` вместо `app.constants.NumberConfigs`.
Поэтому ищется класс, чьё имя равно `B` или оканчивается на `.B`, по ключам индекса классов; больше десяти таких классов — это не адрес.
Нет класса — поиск члена по имени с потолком двадцать, как для методов.

**Не покрыто:** ключи обычного объекта вне `Ext.define` (`const NumberConfigs = {…}`) — в индекс не попадают.
