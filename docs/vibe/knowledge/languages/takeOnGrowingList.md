# `take(n)` на растущем списке отдаёт больше, чем просили

**Дата:** 18.09.2026 · **Повод:** тест знакомства MCP падал через раз под параллельным прогоном

## Что происходит

```kotlin
val seen = CopyOnWriteArrayList<String>()   // дописывает чужой поток
assertEquals(listOf("a", "b"), seen.take(2))
```

Падает сообщением `expected: <[a, b]> but was: <[a, b, c]>` — три элемента там, где просили два.

Причина в реализации: `Iterable<T>.take(n)` сначала смотрит размер, и **если `n >= size`, возвращает
`toList()` — копию всей коллекции**, а не первые n. Между проверкой размера и копированием чужой
поток успевает дописать элемент, и он приезжает в сравнение.

## Что делать

Не увеличивать таймаут — он тут ни при чём, и щедрый срок просто маскирует гонку. Правильно —
дождаться последнего ожидаемого события и только потом сравнивать список целиком:

```kotlin
assertTrue(awaitSeen(server, "notifications/initialized"))
assertEquals(listOf("a", "b", "notifications/initialized"), seen.toList())
```

## Где ещё смотреть

Везде, где мы берём «первые несколько» из коллекции, которую пишет другой поток: ленты вызовов,
журналы событий, накопители потока. `take`, `first`, `drop` и `toList` на такой коллекции дают
снимок неизвестного размера — сравнивать их с точным ожиданием можно только после того, как запись
заведомо кончилась.
